# Note format

This page describes how a campaign is kept in plain Markdown notes. The plugin reads every note through it, and writes to notes only in the ways it lists. Every screen links here, and none invents its own storage.

This page changes as the project does. The project grows in small steps, so parts of this page are still planned. Whoever's change makes any of it untrue updates it in the same change. The syntax is on trial and will change as it is used at the table.

Three rules hold everywhere:

- **The notes are the record.** Answers, statuses, holders and sheet values are all lines in notes. The plugin keeps nothing of its own but the [Campaigns folder](#the-campaigns-folder) you chose, the campaign you were last in, whether its [welcome page](#welcome-page) is done with, the last version whose [news](#whats-new) you saw, and which campaigns have had the [notes of their earlier sessions](#kind-notes) made, so a vault synced to a tablet carries everything with it. On each device, and never in the vault or `data.json`, it also keeps what was typed and not yet saved and whether you agreed to [bringing your character in from D&D Beyond](#the-dd-beyond-agreement), so that answer never travels to another device.
- **Nothing you write is moved or rewritten.** A change is recorded as a new line that names the earlier one (see [Following up](#following-up-an-earlier-line)). The plugin adds lines and never edits one, except a `$` ledger entry you change from the Party funds page, or the price on an item's `:sold` line, or a value's line on a character's own note that you change in the character dialog or on their sheet, which are rewritten where they stand, or the whole text of a note you change and save on its [note page](#note-page), or of a session you change and save with *Edit all* on the [Session notes](#session-notes-page) page, or the file names of the sessions after one you delete, and the names in the `[[Session N]]` links that point to them, which *Delete session* renumbers (and with them the file names of those sessions' kind notes and the `session` link in their properties) (see [Session notes](#session-notes-page), and [Making, renaming and deleting a character](#making-renaming-and-deleting-a-character) and [Character sheet](#character-sheet)). It deletes lines only when you ask it to: *Clear notes* on the Session notes page empties a session below its properties, *Delete session* moves its note to the trash and numbers the sessions after it again, clearing a value in the character dialog, or clearing an override from the sheet, removes the lines on the character's note that state it on their own, reopening a question or changing its answer removes the old answer line (two answers would leave the question unclear), setting a quest active again or changing its outcome removes the old outcome line, and deleting a question or quest removes it with its own follow-up lines. No change is written that would turn lines into a note's properties, as removing the line before a `---` at the top of a note could; the plugin refuses and says so. The other changes it makes to what you wrote are to a campaign's main note, when you change its background picture or wash in the plugin's settings (see [Campaign](#campaign)), to the `holder`, `lines` and `aliases` properties of an item's note, which it keeps up to date from the session lines (see [Items](#items)), and to the properties of the [kind notes](#kind-notes) it makes, which it can also move to the trash when their last line goes and nothing of yours is in them.
- **It reads without the plugin.** With the plugin off, every note is still plain, sensible Markdown, and the links still work.

The plugin writes through `Vault.process`, which reads and changes a note in one step, so nothing written in between is lost. It uses only Obsidian's own vault access, so it works the same on mobile.

## The Campaigns folder

The plugin works inside one folder of the vault, the **Campaigns folder**, and leaves the rest of the vault alone, apart from the links Obsidian updates when a character is renamed (below). It is any folder at any depth, such as `D&D` or `Games/D&D`, chosen in the plugin's settings (*Campaigns folder*, *Choose folder*) or on the [welcome page](#welcome-page), which can also make it. There is no default: until one is chosen, nothing is a campaign and the plugin reads and writes nothing. The vault itself can't be the Campaigns folder, nor can a hidden folder (one whose name starts with a dot, such as the vault's own `.obsidian`) or a folder inside one, and a path with `..`, a backslash, a slash at its start or a part ending in a dot or a space (which Windows trims, so `.. ` would climb out) is refused. The vault's settings folder and the folders inside it are refused too, by name, even under a name without a dot, and whatever the capitals, spaces, invisible characters or way of composing letters it is written with (a disk that ignores capitals takes `Config` for `config`): by the folder picker, by *Make the folder*, when a folder is chosen and when the plugin starts, and the gatekeeper lets nothing through while the Campaigns folder is one of them. The plugin keeps the path in its own `data.json`; a saved path that breaks the rules above is dropped when the plugin starts, which leaves the plugin touching nothing until one is chosen again.

- **Only inside.** Every read, write, new note or folder, rename, trash, listing, file event and lookup of Obsidian's file metadata goes through one gatekeeper (`src/fence/`, entered through `Gatekeeper`; [the source scan](#the-source-scan) checks that no other code goes round it), which checks the path is inside the Campaigns folder and refuses anything else, including a path that climbs out with `..`. A path the plugin makes, for a new note or folder or a rename, must also be written as Obsidian writes it, with every part a name a file can have (if a folder inside the Campaigns folder isn't, making a note in it says to rename the folder in Obsidian); a file already in the vault needn't be, so a note such as `Zoë.md` written in decomposed letters by a Mac or a sync, or a name with a pasted no-break space, still shows. The one exception: a file or folder whose name ends in a dot or a space, such as the folder in `D&D/Pale Moon/Places./Inn.md`, is left out without a word, with everything inside it. Windows drops that ending, so a part such as `.. ` would climb out of the Campaigns folder, and the plugin refuses every such part rather than tell them apart. Such a file shows in no list, its changes are ignored, and the plugin never reads or writes it; rename it in Obsidian's file list to bring it in. A refused write or read fails with a message; a refused lookup finds nothing. Files outside the Campaigns folder don't show in any list, and changes to them are ignored.
- **A report of what it wrote.** The gatekeeper also reports each text it saved through `Vault.process`, each note it trashed and each file it renamed (`Gatekeeper.written`, which only listens: the gatekeeper's own files are the only ones that may tell it anything, which the [source scan](#the-source-scan) checks). It is how the plugin knows a session was saved on this device, so that [kind notes](#kind-notes) are made from saves and never from a change that arrives by sync, and how kind notes follow *Delete session*. Nothing is reported for a change it refused, and a listener that throws can't stop the write or hide the report from the others.
- **Links that lead out.** To the plugin, a link in a campaign note to a note or picture outside the Campaigns folder is a link to a note that doesn't exist: a `background` picture outside it shows nothing, and a character there has no sheet. Pressing a link in the campaign tab opens only a note inside the Campaigns folder; the note it leads to outside is never opened. As in Obsidian, a middle click or Ctrl-click (Cmd-click on a Mac) opens the note in a new tab, and a plain press in the tab in use. A link that leads outside, or to a note that doesn't exist yet, instead opens a note the link names inside the campaign of the note holding the link, looking only at that campaign's notes, much as Obsidian does: first the note at the link's path from the campaign folder (`[[Places/Inn]]` opens `<campaign folder>/Places/Inn.md`), else a note whose path ends with the link's path (`[[Old Mill]]` opens `<campaign folder>/Places/Old Mill.md`), the one nearest to the note holding the link when several do, then the first by path. Capitals, invisible characters, the kind of space and the way letters are composed don't matter, as in the name check for new characters. When no note there matches, it makes nothing: a message says the note doesn't exist inside the campaign yet, as it does when the note holding the link isn't in a campaign. Nothing is ever made by pressing a link. The plugin never reads the note outside, and it changes only when Obsidian updates its links to a renamed character.
- **Renaming a character.** Renaming a character uses Obsidian's rename. If *Automatically update internal links* is on in Obsidian's settings, Obsidian also updates links to that character in notes outside the Campaigns folder.
- **Opening files.** Only files inside the Campaigns folder can open in the campaign tab. Every other file opens in Obsidian as normal.
- **Moving out.** A note moved out of the Campaigns folder is outside the plugin's reach: to the plugin it is deleted, and it never learns where it went. Its note page can't save it any more, and *Open in Obsidian's editor* opens nothing; open it from Obsidian's file list. Lines typed for a session moved out are kept as for a deleted session. When the campaign you are in is moved out (or deleted), no campaign is open until you open a note of another one; the campaign you were in is never followed out of the Campaigns folder, and a campaign saved in `data.json` that isn't inside the Campaigns folder is dropped when the plugin starts.
- **Moving in.** A note or campaign moved into the Campaigns folder from elsewhere in the vault is picked up as a rename, from the path it had to its new one, so drafts kept under its old path and the campaign tab follow it, as they would a rename inside the folder.
- **Changing it moves nothing.** Choosing another Campaigns folder only changes where the plugin looks. Then, as when Obsidian starts, the campaign of the open note opens if it is in the new folder, or else the campaign you were in, or else the first campaign there; with none there, no campaign is open. Lines typed for sessions in the old folder stay where they are, and aren't set aside as gone. Renaming or removing the Campaigns folder in Obsidian doesn't follow it: until it is chosen again, the welcome page asks for the Campaigns folder, as on a new install.
- **One network call.** Every pull request and release checks the two built files the release publishes for known kinds of network code, and fails if it finds any, but for the one call to D&D Beyond described next. In `main.js`: any module but `obsidian`, `@codemirror/state` and `@codemirror/view`; any `http`, `https`, `ws` or `wss` address, or one starting `//`, but the app's own `app://` and capacitor localhost file addresses; `fetch`, `request`, `requestUrl` (but for that one call), `Cookie`, `Authorization`, `withCredentials`, `ajax`, `ajaxPromise`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `sendBeacon`, `RTCPeerConnection`, `Image`, `Worker`, `SharedWorker`, `importScripts`, `import(`, `open` on a window or called on its own, `location`, `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `srcdoc`, `sanitizeHTMLToDom`, `DOMParser`, `createContextualFragment`, `setHTMLUnsafe`, `parseHTMLUnsafe`, `write` and `writeln` (which a document has) on anything, the words `submit` and `requestSubmit` (which a form has), `click` and `dispatchEvent` anywhere, `MouseEvent`, `PointerEvent`, `Audio`, `FontFace`, `CSSStyleSheet`, `adoptedStyleSheets`, `caches`, `Notification`, `image-set(`, any `url(`, an element made with a tag that isn't written in place (`createEl`, `createElement`, `createElementNS`, `createSvg`), an attribute set with a name that isn't written in place or that starts `on` (`setAttribute`, `setAttr`, `toggleAttribute`), CSS set from code (`setCssProps`, `setCssStyles`, `setProperty`, `cssText`), Node's `process` (which can load Node's modules without `require`), `getBuiltinModule`, `mainModule`, `_load`, `dlopen`, and `img`, `image`, `link`, `script`, `style`, `iframe`, `audio`, `video`, `source`, `embed`, `object`, `track`, `meta`, `form` or `base` elements. A few pieces of the plugin's own code are let through, each only written exactly as it is and exactly as many times as the plugin holds it, so one more anywhere is found: the one call to D&D Beyond, `.requestUrl)({ url: beyondAddressOf(id), method: "GET", throw: false })` (once, whatever number Obsidian's import is given in the built file), and its address, `"https://character-service.dndbeyond.com/character/v5/character/"` (once), the `url("…")` the background picture builds from the app's own file address (once), a link's `role: "link"` (once), the welcome page's name form (once), a check for a saved draft's `base` (once), the settings saver's and draft keeper's own `this.write(…)` (three times), the dialogs' own `this.submit()` (four times) and two of their `submit() {` methods, the welcome form's submit button and its `submit` listener (once each), the plugin's click listeners (`addEventListener("click", …)` 25 times and `registerDomEvent(…, "click", …)` 14 times), the character picker's `dispatchEvent(new Event("input"))` (once), and the two `setCssProps` calls that show the background picture (once each). In `styles.css`: any `url(` but a base64 data URL, `@import`, any web address, and escaped letters that could spell either. It looks for known patterns; it is not a proof, and code written to hide from it could get past.
- **The one network call, in the source.** The source scan lets exactly one file name `requestUrl`: `src/online/beyond-call.ts`, which imports it from `obsidian` and calls it once, with one object written in place holding exactly `url`, `method` and `throw`, where `url` is a call of `beyondAddressOf` (from `src/online/beyond-address.ts`) given a `CharacterId`, `method` is `"GET"` and `throw` is `false`. No headers, no body, no other option. No file, that one included, may name `request`; no other file may name `requestUrl` at all, by import, alias, call, value passed on, spread, computed key or string. A `CharacterId` is made only by `CharacterId.of`, which keeps 1 to 12 digits from a bare number or a `dndbeyond.com/characters/<digits>` link and refuses everything else; no file outside `src/online/` may cast to it, check that a value satisfies it, extend it or build it with `new`. `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource` and the rest stay refused everywhere by the rules above, `src/online/` included.

### The source scan

A test, run by `npm test` on every pull request and release, reads as TypeScript, with the type checker, every file the plugin's bundle loads from `src/main.ts` outside `node_modules` (`tests/fence/scan/running/source-scanner.ts`, with one rule family per file in `tests/fence/scan/vault-rules/`, `tests/fence/scan/page-rules/` and `tests/fence/scan/code-rules/`). It is a check of allow-lists and known patterns, not a proof: code written to hide from it could still get past, so every change is also reviewed by hand. It fails `npm test`:

- **When it can't read the code.** A JavaScript, `.mts`, `.cts`, `.tsx` or `.jsx` file in `src/`, a JavaScript or declaration file the entry point loads, or a file esbuild bundles that the scan didn't read (or one it read, holding code, that esbuild doesn't bundle, as a `browser` map in `package.json` could cause).
- **Allow-lists.** A new name is refused until it is listed in `tests/fence/allowed/`; the import, page-global and page-member lists are tested to hold exactly what the plugin uses today, so a name it stops using leaves them:
  - Imports: only `obsidian`, `@codemirror/state` and `@codemirror/view`, and from `obsidian` only the names each area imports today (an area is named by the start of a path, so `settings/` covers the folders inside it); a default or namespace import of it, or `export *`, is refused. Obsidian's file system adapters (`FileSystemAdapter`, `CapacitorAdapter`, `DataAdapter`), `readLocalFile`, `mkdir`, `getBasePath` and the adapter's other path readers, and `MarkdownPreviewRenderer` are refused everywhere, `src/fence/` included.
  - Globals: plain JavaScript ones (`Array`, `Map`, `JSON` and the like) anywhere; `document` and `window` only in `src/main.ts`, `setTimeout` and `clearTimeout` only in `src/views/dialogs/second-press.ts`, and `Event` only in the character picker. `setTimeout` and `setInterval` must be called with a function, never text.
  - The page: elements only of the tags the plugin makes today, named in place; attributes only of the names it sets today, named in place (none starting `on`); `createEl`, `createDiv` and `createSpan` options only those used today, written in place, with `href` only to `#`; `setCssProps` only with a `PictureCss` value; no writes to an element's style or to `href`, `src` and the other members that load from an address. `registerMarkdownPostProcessor` only in `src/main.ts`; reading the page's text (`textContent`, `innerText`, `outerText`, `nodeValue`, `wholeText`, a text node's `data`, ranges and serializers) only in `src/reading/colour-markers.ts`, which colours a session note's markers after asking the fence; looking elements up (`querySelector`, `closest`, `find` and the like) only there and in the three files that find rows on the plugin's own pages.
  - Page members: each file may use only the members of the browser's page (`lib.dom.d.ts`, and Obsidian's additions to its elements) it uses today. Only `src/reading/colour-markers.ts` may reach past its own elements (`ownerDocument`, `doc`, `body`, `parentElement`, `childNodes`, `children`, siblings, `getSelection`, a text node's `data`, `getAttribute`, `dataset`, `attributes` and the like).
  - Computed keys: a key not written in place only in the files listed, and there only when its type is a number or string names other than `constructor`, `__proto__` and `prototype`. A cast that narrows a value to a key name or number is refused anywhere.
  - Each other allowance is by exact file, and the test fails if a file stops needing it: the five gatekeeper files may reach the vault; `campaign/reading/editor-text.ts` reads the editor's text for live typing; `editor/marker-decorations.ts` uses CodeMirror for the marker colours; `characters/pages/characters-view.ts` reads what Bases lists; `settings/drafts/draft-record.ts` reads the keys of the saved drafts; four files cast through `unknown` or `any`; five open notes, five show the campaign tab, and so on.
  - The allowances matched by the start of a path can't be widened by editing their key: `tests/fence/source-checks/allowance-keys.test.ts` checks that every page-member and page-global key names one existing file, and every key for the `obsidian` names one existing file or one existing area folder.
- **Known patterns.** Outside its allowances, no file may:
  - reach `vault`, `fileManager`, `metadataCache` or `adapter`, by name, literal or computed key, destructuring or `Reflect`; read every key of a value that could reach them (`Object.values`, `keys`, `entries`, `getOwnPropertyNames` and the like, `JSON.stringify`, `structuredClone`, spread or `for…in`); take `Object` other than to call one of its functions; or hide such a value by putting it where a type that can't reach goes. `{}`, `Object`, `object`, a function, a type that holds `app` or `workspace`, and a `Pick` of a type that reaches all count as able to reach, and a cast from them counts as loose;

  - read or write the text of Obsidian's editor or a note's view; load CodeMirror, reach its state, document or views, or hook into the editor; read a note's text through a post-processor's context, a view's modes, a view element's text or what Bases lists;

The gate's exemptions from these patterns (walking the vault's folders, forging the gate's types, and listening to a workspace event whose name it can't read) belong to the whole of `src/fence/gate/`, on purpose: a file added to that folder gets them, so it is reviewed as part of the gate. `src/fence/paths/` has none of them.

## Campaign

A campaign is a folder directly inside the [Campaigns folder](#the-campaigns-folder). Every note inside it, and in the folders inside it, belongs to the campaign. A folder deeper down, or a note directly in the Campaigns folder, is not a campaign.

The folder's main note sits at its top and has the folder's name. Its properties hold the campaign's settings:

```
D&D/
  Curse of the Pale Moon/
    Curse of the Pale Moon.md
    Sessions/
      Session 12.md
      Session 13.md
    Characters/
      Mira.md
      Brother Aldric.md
    Fallen/
      Thessaly.md
    Items/
      Silvered lantern.md
    Questions/
      Session 12.md
    Quests/
      Session 12.md
    Funds/
      Session 12.md
```

```markdown
---
role: player
character: "[[Thessaly]]"
party:
  - "[[Thessaly]]"
  - "[[Mira]]"
system: "[[D&D 5e]]"
background: "[[pale-moon.jpg]]"
wash: balanced
---
```

| Property | What it holds |
|---|---|
| `role` | `player`, `dm` or `researcher`. The plugin reads one value: exactly `dm` makes it ask you what a name is (see [A DM's campaign](#a-dms-campaign)). Any other value, a different capital (`DM`), or no `role` at all changes nothing |
| `character` | Your own character, for a player. The dashboard and the Characters page show them first, before everyone else, and set them subtly apart. The plugin writes it only when you choose who is your character (see [Leaving play](#leaving-play)) |
| `party` | The party members, used by `$ split` |
| `system` | The note that describes the game system |
| `background` | A picture in the Campaigns folder, shown behind the campaign tab |
| `wash` | How much of the picture shows: `subtle`, `balanced` (the default) or `strong` |

Renaming the folder renames the campaign. Obsidian renames the main note's links along with it.

**Background:** the campaign tab shows the `background` picture of the campaign you are in behind its sidebar and pages, under a wash of the page colour. A subtle wash lets the least of the picture through and a strong one the most. Text never sits on the picture: the sidebar, the bottom bar and each page's content are on solid panels of the page colour, so every text and marker keeps at least 4.5:1 contrast whatever the picture, and the picture shows only around and between them. The one exception is the box on the *Session notes* page, which shows the picture faintly while you aren't typing in it (see [Session notes page](#session-notes-page)). On a phone or a narrow tab little of it shows. Changing the `background` or `wash` of the main note, or moving to another campaign, changes the picture at once. A `background` that links anything but a picture (avif, bmp, gif, jpeg, jpg, png, svg or webp), or a picture no longer in the vault or outside the Campaigns folder, shows nothing. A note moved into a campaign's folder while it is open in Obsidian's editor shows the picture behind its text there, under the same wash, until it is opened again. Notes outside every campaign, and the plugin's dialogs, keep the plain background.

**Campaign settings:** the plugin's page in Obsidian's settings starts with the *Campaigns folder*, the folder chosen or, while there is none, that the plugin reads and writes nothing until one is chosen, and *Choose folder*, which lists the vault's folders by path to pick from, leaving out the vault itself, hidden folders, Obsidian's settings folder and any folder whose path the plugin refuses. Below it, it shows the campaign you are in, by name: its folder, its background picture and how much of the picture shows. The campaign you are in is the one whose note you opened last, or the one chosen on that page. The plugin keeps it in its own `data.json`, follows the folder when it is renamed, and starts in it next time unless a note of another campaign is open. The same page has *Show this again* under *Welcome page*, which opens the welcome page in the campaign tab, behind the settings window. Choosing a picture from the Campaigns folder writes `background: "[[<picture>]]"` to the main note, **Remove picture** deletes the `background` property, and choosing how much shows writes `wash`. These writes go through Obsidian's own property editing, which writes the whole properties block again: comments in it can be lost, quoting can change, and a main note without properties gets a properties block at its top. The text below the properties is left as it is.

**The campaign tab:** the plugin shows the campaign you are in as one tab, laid out like the prototype: the campaign's name and a sidebar of pages, *Dashboard*, *Characters* and *Session notes*, then, under *From the notes*, *Questions*, *Quests* and *Party funds*. Pressing a page in the sidebar shows it in the same tab. Questions and Quests show how many are open beside their names. Each ribbon icon and its command (*Open dashboard*, *Open characters*, *Open questions*, *Open quests*, *Open party funds*) opens the tab on that page, or moves the tab that is already open to it, and Obsidian opens the tab on the same page next time. Older versions showed Questions, Quests and Party funds as sidebar panels, and the dashboard and each character sheet as their own tabs; those tabs are closed when the plugin loads, or, for a sheet, opened in the campaign tab on that sheet.

When the tab is narrow (its page area 1023 pixels wide or less: a phone, a tablet held upright, or a narrow tab or split on a computer), the sidebar becomes a bar along the bottom of the tab with *Home*, *Cast*, *Notes* and *Funds*, each a symbol above its short name, the current page marked. Questions and Quests aren't in the bar: the dashboard's *All questions* and *All quests* open them. On a phone the bar sits above Obsidian's own navigation bar, and on a phone or tablet it keeps clear of the home bar and, held sideways, of the notch and rounded corners at its sides. The page scrolls above the bar.

Opening one of these files, in any way Obsidian opens a file (the file list, a link, the quick switcher, search, back and forward, a new tab or split, or the workspace Obsidian restores when it starts), shows the campaign tab in place of the editor or Bases:

| File | Shows |
|---|---|
| The campaign's main note, `<Campaigns folder>/<Name>/<Name>.md` | The Dashboard |
| A note in the campaign's `Characters` folder | The Characters page, on that character's [sheet](#character-sheet) |
| `<Campaigns folder>/<Name>/Characters.base` | The Characters page |
| A session note, `<Campaigns folder>/<Name>/Sessions/Session <number>.md` | The [Session notes](#session-notes-page) page, on that session |
| A note in the campaign's `Items` folder, or a folder inside it | The Party funds page, with that [item open](#items) |
| Any other Markdown note in the campaign's folder, wherever it is, such as `Old Mill.md` or `Places/Gilded Stag.md` | Its own [note page](#note-page) |

Opening a file of another campaign moves you into that campaign. No Markdown note of a campaign opens in Obsidian's editor any more. A campaign's other files (pictures, PDFs, canvases, and bases other than `Characters.base`) and every file outside a campaign or outside the Campaigns folder still open as Obsidian opens them. There is no way back to the plain note for these files: to change a character's note by hand, edit it with the plugin off, or use *Edit character* and the sheet; to change or remove a line of a session, use *Edit all* on the Session notes page; an item's note and any other note are changed on the note page. Tabs that already show one of these files when the plugin is turned on are switched to the campaign tab. The tab keeps the page and the note it shows, so Obsidian's back and forward buttons step between pages and sheets, and it opens there again next time. When that note is renamed, the tab follows it; when it is deleted, the tab goes back to the page without it, such as the character gallery, but the Session notes page and the note page stay on it, keeping what was typed.

Opening a campaign file while the campaign tab is already open in the same window shows it in that tab instead of opening another: the tab it was opened in goes back to what it showed before, or closes if it showed nothing. A pinned campaign tab is left as it is. Back and forward in a tab step through its own history and never move it.

Turning the plugin off leaves its campaign tabs as Obsidian's placeholder for a view it can't show, until you turn the plugin on again; the files themselves open in the editor and Bases as usual while it is off.

**Note page:** a note of the campaign that no other page shows, such as a place, opens on a page of its own in the campaign tab. It isn't in the sidebar or the bottom bar, and no page there is marked while it shows, as it is reached by opening the note. It shows the note's name as its heading (a [kind note](#kind-notes) in the campaign's `Questions`, `Quests` or `Funds` folder shows its type first and the session's name last, *Questions - Session 1*, whatever its file is called: only the heading changes, never the file name or its links) and the note's whole text, properties and all, in the same plain text box as the Session notes page; this is the one place such a note is changed while the plugin is on. A note in the campaign's `Places` folder also shows *In the notes* below the box, the same list a character's sheet shows (see [In the notes](#in-the-notes)): every session line, in every campaign, with a link to the place: your own campaign's sessions first, then other campaigns by folder name, newest session first within each, and lines from another campaign carry `· <Campaign>` after the session; with how many there are, or *No session mentions [[Old Mill]] yet.* when there are none; pressing a line opens its session at that line. `@[[Old Mill]]` counts, as any link does. Other notes show no such list. It writes nothing.

- *Save*, or Ctrl + Enter (Cmd + Enter on a Mac), writes the box's text as the note's whole text, in one change of the note. It can't be pressed until the text differs from the note, and the box is read-only while it saves.
- Before it writes, it reads the note again, in the same step as the write: if the note was changed anywhere else since the page loaded it (another device, a sync, another app), it writes nothing, keeps what you typed in the box and says so. *Load the note again* then shows the note as it is now; it drops what you typed, so it takes a second press. Copy out what you typed first.
- While nothing is typed, the box follows changes made to the note elsewhere.
- What is typed but not saved stays in the box while you move between pages of the tab and when Obsidian closes and opens again, with the note's text it was typed over, so a change made since is still caught. It is kept on this device only, with the Session notes page's unsaved lines, by note, following a rename, until it is saved or typed back to what the note says. Two boxes open on the same note show the same text: what is typed in one shows in the other.
- When the note is deleted, the page stays on it, keeps the box and what you typed, says the note is gone, and saves nothing.
- Below the box, *Links in this note* lists each `[[link]]` in the box once; pressing one opens that note, in the campaign tab when it belongs to the campaign.
- A note saved with Windows line endings, or with a byte order mark at its start, keeps them when it is saved; the box shows its lines as usual.
- A new note made inside the campaign's folder, such as with Ctrl + N (Cmd + N on a Mac), opens on its note page too.
- The page doesn't rename a note: rename it from Obsidian's file list, and the page follows it. When a note is moved out of the campaign while its page shows, the page says so and offers *Open in Obsidian's editor*, which opens it there in the same tab; it can't be pressed while what you typed is unsaved, so save first. A note moved out of the [Campaigns folder](#the-campaigns-folder) altogether can't be saved or opened from the page: copy out what you typed, and open the note from Obsidian's file list.
- Obsidian's templates are inserted in its editor, so they can't be inserted into a campaign note while the plugin is on; paste the template's text into the box instead.

The page never deletes a note.

<a id="new-campaign"></a>**New campaign:** *New campaign*, the last entry of the campaign switcher (see below), opens a small window asking for the campaign's name, with *Make campaign*. It makes `<Campaigns folder>/<Name>/<Name>.md` with an empty main note (a main note without properties is a player's campaign, see [Campaign](#campaign)), exactly as *Make a campaign* on the welcome page does, makes it the campaign you are in and opens the Dashboard. A name that is empty, that a note's file can't have, or that a folder or file in the Campaigns folder already has, even with other capitals, is refused in words as a notice, nothing is made, and the window stays open with the name still typed. Nothing that exists is ever overwritten. With no Campaigns folder chosen it says so.

<a id="campaign-switcher"></a>**Campaign switcher:** at the top of the campaign tab's sidebar, beside the name of the campaign you are in, a small arrows button (*Switch campaign*) opens Obsidian's own menu. It lists the campaigns found in the Campaigns folder by name, in order, with the one you are in ticked, then a line and *New campaign*. Choosing another campaign does what the *Campaign* choice in the plugin's settings does: it becomes the campaign you are in, is kept in `data.json`, and the tab follows. It is a button, so Tab reaches it and Enter or Space opens the menu, whose arrow keys and Enter are Obsidian's; it is at least 44 pixels square for touch. It is on every page of the tab, the welcome page too, and also when no campaign is open, where the menu holds only *New campaign*. Only folders that hold a main note of the same name are listed, so a folder that is not a campaign never shows. The list is read each time the button is pressed; if the campaign chosen was removed while the menu was open, or is already the one you are in, nothing changes, and a removed one says so as a notice. A long name wraps in the sidebar and is shown as Obsidian's menu shows it. On a narrow screen, where the sidebar becomes a bottom bar that doesn't show the name, the switcher stays at the left end of the bar (at least 44 pixels wide and as tall as the bar), and its menu opens at the button, kept on screen by Obsidian.

<a id="welcome-page"></a>**Welcome page:** the first time the plugin is turned on in a vault, the campaign tab opens by itself on a *Welcome* page. Like the note page, it isn't in the sidebar or the bottom bar. It shows three short first steps: that the campaign lives in this tab and the sidebar (or, on a phone, the bottom bar) moves around it; that *New session* starts a session, where a line starting with `?` is a question, `!` a quest and `$` coin or an item; and that opening any note of the campaign comes back to the tab. Below them is one button: *Start my first session* while the campaign has no session notes, or *Go to my campaign*, which shows the Dashboard, once it has. While no [Campaigns folder](#the-campaigns-folder) is chosen, the button gives way to what it is for and *Choose a folder*, which lists the vault's folders to pick from, leaving out the same ones as *Choose folder* in the settings, with a box and *Make the folder*, which makes the folder typed (such as `D&D` or `Games/D&D`, refused as the vault itself, a hidden folder, with `..` or with a part a file can't be named) or uses it if it is there already, and chooses it. Once it is chosen and holds no campaign yet, the page shows what a campaign is (a folder inside the Campaigns folder holding a note of the same name) and *Make a campaign* with a box for its name, which makes `<Campaigns folder>/<Name>/<Name>.md` and moves you into it; a name a note's file can't have, or one already used by a folder or file in the Campaigns folder, even with other capitals, other invisible characters or another kind of space, is refused and nothing is made. Names elsewhere in the vault don't matter. The name is taken as Obsidian writes a path, so a non-breaking space in it becomes a plain one. If the main note can't be made, the new folder is removed again, as long as it is still empty, and the message says why the note failed and names the folder if it couldn't be removed. If the campaign is made but moving into it fails, the message says so; open its main note to move in. Once there is a campaign, a device that hasn't agreed to [bringing your character in from D&D Beyond](#the-dd-beyond-agreement) gets one more step before the button: *Bringing your character in*, with the agreement's words, *Agree* and *Not yet*. Either answer moves on to the button; *Not yet* keeps nothing, so the step comes back only when the page is shown again with *Show this again*, and the first press of the online button asks again. The page shows by itself once per vault (`welcomeSeen` is in the synced `data.json`), so a second device that syncs the vault never shows the step and is asked only at that first press. Before it opens the page, the plugin writes `welcomeSeen: true` and `lastVersionSeen` (this version) to its `data.json`, so the page shows by itself only once per vault, and not at all if `data.json` can't be written; *Show this again* in the plugin's settings opens it any time. The one exception is the Campaigns folder: while none is chosen, on a new install or after an update alike, the campaign tab opens on the welcome page at every start, and every page of the tab, from the sidebar or a command, shows the welcome page asking for it instead. The plugin doesn't know whether it was installed before. It takes a vault for an update when its `data.json` already has `welcomeSeen`, or when a campaign in the Campaigns folder already has a session note the first time this version runs; the second gets `welcomeSeen` only, no welcome page, and the update's news, below. An update from 0.2.0 or earlier has neither: those versions never wrote `welcomeSeen`, and with no Campaigns folder chosen yet no campaign can be found. So it is taken for a new install: the welcome page opens, asking for the Campaigns folder, and `lastVersionSeen` is set to this version, so any news this version lists doesn't show.

<a id="whats-new"></a>**What's new:** after an update whose version lists something new, the Dashboard shows one line above its panels: *New:* and one sentence, then *Show me*, which opens the page it is about, and *Dismiss*. Either one hides the line and writes the version to `lastVersionSeen` in `data.json`, so each update's line shows until it is pressed and never again. What a version lists is written by hand in the plugin's code, one sentence per version at most, so nothing is announced by accident; most versions list nothing, and show no line. A fresh install counts its own version as seen, since the welcome page covers it.

**Dashboard:** the campaign tab's first page shows where the campaign stands. It writes nothing and keeps nothing: each panel counts from the same lines as its full page, so the numbers match, and redraws as you write. Each panel opens its full page:

| Panel | What it shows | Opens |
|---|---|---|
| Open questions | How many, and the three newest | *All questions*: the Questions page |
| Active quests | How many, and the three newest | *All quests*: the Quests page |
| Purse | The purse, how many items are held, money in and out, and the three latest entries | *Party funds*: the Party funds page |
| Characters | Each note in the campaign's `Characters` folder with its class, AC and HP, the player's own first and marked *Your character*, then the rest by name | *All characters*: the Characters page |
| The latest session | Its heading, such as *Session 13 · The ferry at dusk*, how many questions, quests, coin entries and items were written in it, and every one of those lines, the last written first, in a list that scrolls | *Write notes*: the session's Notes page. *New session* starts the next one |

The latest session's panel is the first one. Its list is as tall as three or four rows and scrolls past that, so the most recent quest, question and coin or item line of the session are all in it. An item line shows the item's name and what the line did (*Item* for a first mention, *Changed*, *Sold*, *Used up* or *Lost*). A sale (`$$ Lantern :sold 30gp`) is one row, its coin entry, not a second row for the item. Tapping a question, quest, coin entry or item opens its dialog, as on its own page, and tapping a character opens their sheet. When two session notes share the highest number, it isn't clear which is the latest, so the panel shows no session and says to rename one, as the dialogs that write into the latest session do.

## Session

A session is one note in the campaign's `Sessions` folder, named `Session <number>`. The number sets the order: the newest session is the one with the highest number.

```markdown
---
played: 2026-03-14
title: The ferry at dusk
---

Tracks lead to the [[Old Mill]].
? Why does the Old Mill wheel turn at night
! Find the missing caravan, from: [[Lady Vess]], reward: 200 gp
$ 35 gp 4 sp from the bandits at the ford
```

| Property | What it holds |
|---|---|
| `played` | The date it was played, `YYYY-MM-DD` |
| `title` | Optional. Screens show *Session 13 · The ferry at dusk* |

**New session:** creates `Sessions/Session <highest + 1>.md` with `played` (the date chosen, today by default) and, if one is given, `title`. Nothing else is copied into it. The campaign tab then shows its [Notes page](#session-notes-page), ready to write in.

### Session notes page

The campaign tab's *Session notes* page is where a session is written. It shows the session asked for (opening a session note, choosing one, or *Write notes* on the dashboard), or else the latest one, and then stays on that session even when a newer one arrives; when two sessions share the highest number it shows none and says to rename one, as the dashboard does.

- **The header** shows the session, such as *Session 12 · The Old Mill*, a list of the campaign's sessions to switch between, newest first, each with its title and the date it was played (*Session 12 · The Old Mill · 9 Nov 2026*, leaving out what is blank), and *New session*.
- **The box** is a plain text box: no colours while typing. In a campaign with a `background`, it shows the picture at a fifth of its strength, softened, while you aren't typing in it, so typed lines keep at least 4.5:1 with the sample themes the tests check; the example line in it is hidden then. Tapping into it fades the picture out and shows the example line again. Each line is typed as it would be in the note (`? Who sent the letter`, `! Find the caravan, from: [[Lady Vess]], reward: 200 gp`). *Save*, or Ctrl + Enter (Cmd + Enter on a Mac), adds every line that isn't blank or a lookup, trimmed, to the **end** of the session note, after a line break, in one change of the note. Nothing already in the note is moved, changed or removed, and its properties stay as they are. Lookup lines stay in the box; the rest is cleared. *Save* can't be pressed while there is nothing to save. While a save runs, every box for that session is read-only, so nothing typed is lost and nothing is written twice. If the note can't be written (the lines would turn into its properties, or the note is gone), nothing is written, the lines stay in the box and the page says why. Every box open for the same session shows the same text: what is typed in one shows in the others. When the session's note is deleted, the page stays on that session, locks its box and says the note is gone; it never moves to another session on its own. What was typed in the box and not saved is kept under *Kept from deleted sessions* on the Session notes page, with the session's name and when it was deleted, so a new session made with the same name starts with an empty box. Lines typed for a session whose note is no longer there when Obsidian opens (removed while it was closed; this is checked only once a Campaigns folder is chosen, so an update that has none yet sets nothing aside), or left under a path another session is renamed onto, are set aside the same way under *Kept from missing sessions*. *Copy into this session's box* adds those lines after what the box of the session shown already holds; *Discard* drops them on a second press. What is typed but not saved stays in the box while you move between pages of the tab and when Obsidian closes and opens again: it is kept **on this device only**, in Obsidian's storage for this vault, not in the vault or the plugin's settings file, so it doesn't sync to other devices. It is kept by session note, following a rename, until it is saved or emptied, written half a second after typing stops and again when Obsidian quits, the plugin is turned off, or the app is put in the background or its page hidden (as on a phone). If the device doesn't keep it, a notice says so. Lines that an earlier version kept in the plugin's settings file are moved to each device once, never into a box: they are listed under *Kept from an earlier version*, with the session's name and when they were moved, to copy or discard on that device. They are taken out of that file only after the device has kept them.
- **Lookups:** typing `??`, `!!` or `$$` and a few words on a line of the box suggests the open questions, active quests or held items that hold every word, as in a note (see [Following up](#following-up-an-earlier-line)): ↑ and ↓ move, Enter or a click picks, Esc closes. Picking removes the lookup line from the box and opens the dialog, which writes its follow-up line into the session shown. Lookups are suggested only in this box, never in Obsidian's own editor.
- **Notes** lists the lines of the session note below its properties, newest first: the last line in the note, written last, is at the top. It shows how many there are. Each line shows its mark (`?`, `!`, `$`, or `?=`, `$$` and the like) in its colour, and its links as links that open the note linked. A question that is answered and a quest that is completed show ✓; a quest abandoned and an item sold, used up or lost show ✕ and are struck through. Pressing a line (or Enter or Space on it) opens the dialog the dashboard opens for it: the question's or the quest's dialog, an item's dialog for a line that names or changes an item (a sale included), or a coin entry's dialog. Closing it puts the focus back on the line. A line no dialog edits (plain text, and a follow-up such as `?=` or `!x`, which is changed from the dialog of the line it follows) can't be pressed; use *Edit all* for those. A link inside a line still opens its note. The list redraws whenever the note changes.
- **Edit all**, beside the *Notes* heading, is for fixing what is already written, such as a typo in an old line. It shows the session note's whole text, properties and all, in a box in place of the box for adding lines and the list, which are hidden until you leave. It saves exactly as a [note page](#note-page) does: *Save* or Ctrl + Enter writes the box's text as the note's whole text in one change, and only if the note hasn't changed anywhere since the box loaded it (otherwise it writes nothing, keeps what you typed and says so, and *Load the note again* takes a second press); Windows line endings and a byte order mark are kept; what is typed but not saved is kept on this device, with the note's text it was typed over; and when the note is deleted, it says so and keeps what you typed. *Done* goes back to adding lines. With changes not saved, *Done* says so instead of leaving, and offers *Keep editing*, or *Back to adding lines*, which leaves them kept on this device: *Edit all* then reads *Edit all (not saved)*, a note above the box for adding lines says an *Edit all* change isn't saved yet, and pressing *Edit all* shows them again. Moving to another session or page keeps them the same way. Lines added to the session before those changes are saved change the note, so *Edit all* then writes nothing and says the note has changed: copy the change out, load the note again and make it again.

- **Clear notes** and **Delete session**, beside *Edit all*, both remove what was written, so each asks first in a dialog, where *Esc*, a click outside or the keep button (which has the focus) changes nothing. Neither can be pressed while a save of this session runs, and *Clear notes* can't be pressed while the session has no lines. Only one of these dialogs is open at a time. If a save starts while the dialog is open, nothing is done and the page says so. While clearing or deleting runs, the box for adding lines can't be saved.
  - *Clear notes* asks *Clear the notes of Session 12 · The Old Mill?*, saying how many notes go (*Its 4 notes go, including any questions, quests and ledger lines first written in them. The session and its properties stay.*), with *Clear notes* and *Keep notes*. Clearing empties the note below its properties in one change of the note; the properties stay exactly as written, and so does the note, if it changed in any way since the dialog opened, or if it starts with `---` but its properties block can't be read, as when it isn't closed (the page says which). The page stays on the session.
  - *Delete session* asks *Delete Session 12 · The Old Mill?*: *Its 4 notes go with it, including any questions, quests and ledger lines first written in it. Other sessions, and values learned on character sheets, stay.* (*Its 1 note goes with it…* for one, *It has no notes.* for none), with *Delete session* and *Keep session*. Deleting moves the note to the trash Obsidian is set to use (Settings → Files and links → Deleted files), so it can be taken back from there, unless Obsidian is set to delete permanently: then the dialog says the note can't be taken back. Nothing is deleted, and the page says so, if the note changed in any way since the dialog opened or another note has taken its place. Lines typed in its box and not saved are kept under *Kept from deleted sessions*, as for any deleted session. The page then shows the latest session left, or says there are none.
    - **The sessions are numbered again.** After a delete, the campaign's sessions are numbered 1, 2, 3 and so on in their order, with no gaps: with Sessions 1, 2, 5 and 7, deleting Session 2 makes 5 and 7 into 2 and 3. Session 0 stays where it is, and only *Delete session* does this: deleting a note in Obsidian's file list, or one that disappears in a sync, renumbers nothing. The dialog names the sessions that move (*Delete Session 2 · The Old Mill?* … *Sessions 5 and 7 become 2 and 3.*, and nothing more when none moves). A session keeps its title, played date and lines; only its file name changes, from the lowest up, through the Campaigns folder's gatekeeper and Obsidian's plain rename, which updates no link anywhere in the vault. Nothing is deleted or renamed, and the page says why, when two sessions share a number, or when a new name is taken by another file (a `session 3.md` in other capitals counts as taken); the plan is checked again just before the note goes to the trash, and nothing is deleted if the sessions changed since the dialog opened. Lines typed and not saved follow each rename.
    - **Links.** The names in `[[Session 4]]`, `[[Session 4|alias]]`, `[[Session 4#heading]]`, `![[Session 4]]` and `[[Sessions/Session 4]]` links, and the same with the escaped bar of a table cell (`[[Session 4\|alias]]`), are rewritten to the new numbers, in one pass from what is written, so a link to Session 5 becoming 4 is never rewritten again into 3. It is rewritten in every note of the same campaign, and in notes of the Campaigns folder that sit outside every campaign when only this campaign has a session of that number. A link is read the way the campaign tab reads it, and one to the deleted session is left as written, so it then points to the session that took its number. Not rewritten: links in other campaigns' notes (which mean their own sessions), links in a note's properties, in code blocks, in math blocks, on a line that holds a comment (`%% %%`) or `<!-- -->`, in an indented list after a blank line (read as code) and in `inline code`, links written as Markdown links, and, in a note outside every campaign, a link that more than one campaign has a session for, since it isn't clear which is meant. Each note is written as one change that is read back to check that only link names changed.
    - **If something fails.** After the note is in the trash, a notice that stays says which sessions were renamed and which weren't if a rename failed (renaming stops there, and no link is updated), which notes' links weren't updated, and which notes had a link left as written for lack of a clear campaign, and which notes still hold a link to a session that moved on a line that isn't rewritten. After a failed rename the page moves to the latest session that still exists. A link from a note outside the Campaigns folder is never touched, so it can end up pointing to another session or to none.

**What's still open:** above its own text, every session note shows the questions and quests that were still open when it began, wherever they were written. The plugin draws this from the earlier sessions each time the note is opened, the way a character from Session 1 shows on their sheet in Session 30. It is never written into the note, so nothing appears twice, and an answer written in Session 13 shows up everywhere at once.

## Lines

The plugin reads a line by its first character. A list bullet (`- `, `* ` or `+ `) and indentation before it are skipped, so `- ? Who sent the letter` is a question too. A task checkbox (`- [ ] ? …`) or a numbered list item is not skipped, so those lines stay ordinary notes. Any other line is ordinary notes, apart from [character facts](#character).

| Line | Read as |
|---|---|
| `? Who sent the letter` | A question |
| `! Find the missing caravan, from: [[Lady Vess]], reward: 200 gp` | A quest, with who gave it and the reward |
| `$ 35 gp 4 sp from the bandits at the ford` | Coin coming in |
| `$ Paid 5 gp to the ferryman`, `$ -5 gp ferry` | Coin going out |
| `$ [[Mira]] Flame Tongue longsword` | An item, held by the linked character (see [Items](#items)) |
| `$ Potion of healing` | An item the party holds, with no one holding it yet |
| `?? letter`, `!! caravan` | A lookup typed while writing, which finds an earlier question or quest. The plugin never reads it as a note |
| `$$ Silvered lantern :sold 30gp` | Something happened to an item ([Items](#items)) |
| `@[[Old Mill]]` inside a `?`, `!` or `$` line | A link to a place (see [People and places](#people-and-places)). It still shows as an ordinary link |

`src/notes/` reads all of these today, and `src/campaign/` builds a campaign from the session notes in its folder, in session order. [#62](https://github.com/Libertas-le-Spes/dungeons-and-dinthla/pull/62) lists the exact rules: commas, links, signs and the five coin kinds.

### Quest facts

A quest's facts are `name: value` pairs after its title, with the name in any letter case (`From:` reads like `from:`). Each one runs to the next fact or the next comma. As with money, a comma between two digits or inside a `[[link]]` doesn't end it, so `reward: 1,200 gp` and `from: [[Vess, Lady]]` stay whole:

| Fact | Holds | Read today |
|---|---|---|
| `from:` | Who gave the quest | Yes |
| `reward:` | What it pays | Yes |
| `where:` | Where it leads | Not yet |
| `due:` | When it must be done by | Not yet |

### Money

| Line | Read as | Read today |
|---|---|---|
| `$ +120 gp sold the wagon` | +120 gp | Yes |
| `$ [[Thessaly]] +30 gp share` | +30 gp, held by Thessaly | Partly: read as +30 gp with no holder. If Thessaly is your character, the line is on your list (Mine tab), not the party's |
| `$ split 120 gp, [[Mira]] 60 gp` | 120 gp shared among the `party`, Mira's share set to 60 gp | No |
| `$ = 85 gp` | The purse counted: it holds 85 gp from here on | No: read as +85 gp |
| `$ [[Mira]] = 40 gp` | Mira's own purse counted | No |

Each amount on a line counts on its own ([#68](https://github.com/Libertas-le-Spes/dungeons-and-dinthla/issues/68)). An amount is money out when it has its own minus sign, or when *paid*, *spent*, *bought*, *gave* or *lost* comes before it, up to the next comma. A comma between two digits is part of the number, so `paid 1,200 gp` is −1,200 gp, and a comma inside a `[[link]]` is part of the name. A money-out word inside a link is part of a name too, so `$ reward from [[Lost Hollow]] 5 gp` is +5 gp. A sign always wins over a word.

| Line | Read as |
|---|---|
| `$ +50 gp reward, -5 gp ferry` | +45 gp |
| `$ paid 5 gp, got 3 gp back` | −2 gp |
| `$ Bought rope for 2 gp` | −2 gp |
| `$ [[Lady Vess]] gave us 50 gp` | −50 gp: write `+50 gp` when someone gives the party money |

*Add coin* on the Party funds page writes money in as `$ <amount> <what for>` and money out as `$ Paid <amount> <what for>`, into the session you're in. It shows how the line will be read as you type, and saves only if it reads back as exactly the money chosen. It refuses an amount with stray commas, a sign or money word that says the other way, an amount that comes to nothing, and `for:`, which marks a quest's reward collected. Tapping a `$` entry in the ledger opens it the same way: saving rewrites its line where it stands in its own note, keeping its bullet, and *Delete entry* removes it, each only if the line still says what was read, on the line it was read from, and the purse moves by exactly the difference. Saving with nothing changed writes nothing. The dialog only saves an entry it would write back word for word, as *Add coin* words it; any other, such as `$ Bought rope for 2 gp` or `$ +50 gp reward, -5 gp ferry`, can only be deleted there, so change it in its note, which *Open note* opens. A sale's entry belongs to its item's `$$` line, so while that sale is how the item went, tapping it opens the item instead, where its price can be corrected. Once a later line names the item again, tapping the sale opens its note. A new line is also refused when it would land in a code block, `%% %%` comment, `<!-- -->` comment or math block that never closes, where it would be hidden, and nothing is written. The same check runs again on the note's text as it is when the line is written, so a note changed meanwhile (a sync, a second window) is caught too.

**Mine and Party:** the Party funds page has two tabs, *Mine* and *Party*, with *Mine* showing first. They are a tab list: the left and right arrows, *Home* and *End* move between the tabs, and a tab is pressed with *Enter* or *Space*. *Mine* holds your character's purse from their sheet (see [Your character's purse on the Party funds page](#your-characters-purse-on-the-party-funds-page)), *Your purse from the ledger* (the total, money in and out, and the coins it is made of, worked out from your coin lines only, like the party purse, and saying so in words when you have none or no character is named), and the items your character holds. *Party* holds the party purse, the items of anyone else, the party included, and the party's ledger. A `$` line goes on your list when it links one of your characters anywhere on the line, not only first, as in `$ Flame Tongue longsword found by [[Mira]]` or `$ 30 gp from the bandits, share to [[Mira]]`; a `$$` change or sale line does too. Your characters are those the campaign note's `character` property names (a link to the character's note, or several), matched by the note's name whatever the capitals. An item is yours when the last line that gave it a holder links one of them, and it shows under that character's name; a gone item is yours when the `$$` line that sold, used up or lost it links one of them, wherever on the line, whoever held it before. Coin lines that link your character, sales included, are in the ledger and the purse of *Mine*, apart from the party's, and not in the party purse or ledger. Everything else is the party's. A character who has left play and is no longer named there has nothing in *Mine*. Naming or changing your character in the campaign note moves lines between the tabs at once. With no character named, *Mine* says so and everything is in *Party*. The ledger and the items of each tab are in a box of the same height as the latest session's list, which scrolls past that, with the latest first (`Tab` reaches a box, and the arrow keys scroll it). The items of a holder are ordered by the session and line that first names them, the last written at the top; the holders keep their order, and the gone items stay in a fold, the last gone first.

## Following up an earlier line

Answers, progress and changes are new lines, written in the session where they happen. Each one starts with the earlier line's text and a colon, then says what happened:

```markdown
? Who sent the letter                           (Session 12)
?= Who sent the letter: [[Lady Vess]] sent it   (Session 13)
```

You don't type the earlier line's text. Type `?? letter` or `!! caravan` on its own line in the box on the [Session notes](#session-notes-page) page (lookups work only there, not in Obsidian's editor), and the plugin suggests the open questions or active quests holding every word typed, newest first, at most eight, with the words marked. Words are matched as the text reads, so a link matches by what it shows. Pick the line from the suggestions: the lookup line is removed and the question's or quest's dialog opens, as if you had tapped it on its page. Then choose what happened. The plugin then writes the follow-up line into the session you're in: the session the Session notes page shows, or else the campaign's latest. An open session earlier than the question, or than any of its clues or its answer, is passed over, since a follow-up is only read after the line it follows and a clue only while its question is open, and so is an open note whose file is no longer among the campaign's session notes. Each dialog that writes a line (a question, a quest, a coin, an item and a sheet's learned value, new or not) names the session it will write into and never writes into another: if that session's note is deleted, moved or made again while the dialog is open (as when another session is renumbered into its name), saving writes nothing and says *Session 7 was moved or deleted, so nothing was written.*, and the dialog keeps what was typed. You may also type one in full.

A follow-up belongs to the open question or active quest whose text comes right before its colon: `?= Who sent the letter: …` belongs to *Who sent the letter*, never to a shorter *Who*. When the line holds more than one colon, the longest text that matches wins, so a colon inside a question's own text does no harm. For a quest the text is its title, without its facts (`from:`, `reward:`, `where:`, `due:`).

If an earlier line is reworded, its follow-ups no longer match it. The plugin marks a follow-up that matches nothing, so either line can be fixed.

`?+`, `?=`, `!+`, `!=`, `!x` and `$$` lines are read and matched today. `!x` needs a space or the end of the line after it, so a quest can still start with an x. Some parts aren't read yet:

- `after:`, `where:` and `due:` stay part of the question's text or the quest's title, so a follow-up has to include them to match.
- A `for:` line counts as coin in without marking the quest paid.
- A follow-up that matches nothing is collected but not marked yet.

A follow-up typed in full must match the earlier text exactly, capitals included.

### Questions

| Line | Means |
|---|---|
| `?+ Who sent the letter: it smelled of lantern oil` | A clue. The question stays open |
| `?= Who sent the letter: [[Lady Vess]] sent it` | The answer. The question is answered |
| `? Who is the pale woman, after: Who sent the letter` | A new question that follows from the earlier one |

A question is open until it has a `?=` line. Reopening it removes that `?=` line; changing the answer replaces it with a new one in the same note, so later questions keep their clues; a follow-up typed with it still goes into the session you're in, and is refused if a question already reads like it. Before writing an answer, a reopening or a follow-up, the plugin reads the notes as they would be after the change, and writes nothing unless only this question changes as intended. A delete has no such check: it removes only the question's own lines, where they were read. Deleting a question removes its `?` line, its clues and its answer, wherever they were written. The plugin does each only when you ask. It removes a line only if it still says what was read, on the line it was read from; another line that reads the same is never taken in its place. If the question or the answer being replaced has changed or moved since it was read, it writes nothing and says so; deleting a question leaves any clue or answer line that was changed or moved since it was read, and says which notes kept them. Another line that reads like the question is never deleted with it. An answer that would be read as another open question's, because that question starts the same way, is refused. An answer can't be given from the page while an earlier open question reads the same, since the answer would go to that one. A new line is also refused when it would land in a code block, `%% %%` comment, `<!-- -->` comment or math block that never closes, where it would be hidden, and nothing is written. The same check runs again on the note's text as it is when the line is written, so a note changed meanwhile (a sync, a second window) is caught too. When a follow-up goes to a later session than the answer and that later note has such a block, the answer is written and the follow-up is left out, and the page says so: close the block in the note and add the follow-up by hand.

*New question* on the Questions page adds `? …`, and `?= …` if an answer is given, to the campaign's latest session, so the new lines are read after every other. It refuses a question that reads the same as one already asked, open or answered, since their answers would be mixed up, and an answer that would be read as another question's. A new line is also refused when it would land in a code block, `%% %%` comment, `<!-- -->` comment or math block that never closes, where it would be hidden, and nothing is written. The same check runs again on the note's text as it is when the line is written, so a note changed meanwhile (a sync, a second window) is caught too.

### Quests

| Line | Means |
|---|---|
| `!+ Find the missing caravan: tracks lead to [[Old Mill]]` | Progress. The quest stays active |
| `!= Find the missing caravan: found it under the Old Mill` | Completed, with what happened |
| `!x Find the missing caravan: the wagons burned` | Failed or abandoned, with what happened |
| `! Escort [[Mira]] to the ferry, after: Find the missing caravan` | A follow-up quest |
| `$ +200 gp reward, for: Find the missing caravan` | The reward collected. It is coin in, and the quest counts as paid |

Tapping a quest on the Quests page opens it to note progress, complete or abandon it with what happened, collect a coin reward, or open a follow-up quest. Each writes the line above into the session you're in, as answers are. Setting a finished quest active again removes its outcome line, and changing the outcome replaces it. A coin reward of one amount is offered until a `$ … for: <quest>` line for it exists, so it can't be collected twice, and not at all when the quest's own title holds an amount the reward line would also count. Quests sharing a title share that check, and a reward already written by hand in other words isn't recognised, so switch the toggle off for it. A changed outcome is written in the old outcome's note, so a later quest of the same title keeps its lines. Deleting a quest removes it with its progress and outcome lines. The same refusals hold as for questions: a line changed since the dialog opened, an earlier active quest with the same title, or a note that would read as about another quest. A follow-up quest is also refused when a quest already has its title, so saving the same follow-up twice writes it once as *New quest* does. A new line is also refused when it would land in a code block, `%% %%` comment, `<!-- -->` comment or math block that never closes, where it would be hidden, and nothing is written. The same check runs again on the note's text as it is when the line is written, so a note changed meanwhile (a sync, a second window) is caught too. Before writing, the plugin reads the notes as they would be after the change, and writes nothing unless only this quest changes as intended and the purse moves by exactly the reward. Deleting a quest leaves its reward line and its follow-up quests.

*New quest* on the Quests page adds `! <quest>, from: <giver>, reward: <reward>` to the campaign's latest session, so it is read after every other line. *Given by* suggests the campaign's characters; one with a note is linked, by its full path if another note shares its name. It refuses a title already used, and a quest that would read back differently from what was typed, such as one with `from:` or `reward:` in a field. A new line is also refused when it would land in a code block, `%% %%` comment, `<!-- -->` comment or math block that never closes, where it would be hidden, and nothing is written. The same check runs again on the note's text as it is when the line is written, so a note changed meanwhile (a sync, a second window) is caught too.

### Items

The plugin doesn't keep an inventory. It keeps the items that matter to the party, from what you write about them. An item line starts with `$$`, then the item's name, then a space, a colon and one of `changed to`, `sold`, `used` or `lost`. A colon inside the name (`Ring: +1`) is part of the name, because only the last ` :` before one of those words counts:

| Line | Means |
|---|---|
| `$$ Silvered lantern :changed to [[Mira]]` | Mira holds it from here on. The funds screen shows who held it before |
| `$$ Silvered lantern :changed to the party` | The party holds it again |
| `$$ Silvered lantern :sold 30gp` | Sold. The 30 gp goes into the purse |
| `$$ Potion of healing :used` | Used up |
| `$$ Silvered lantern :lost` | Lost |

The funds page shows an item's name as written, with one exception: a name as the import writes it, such as `Rope\_coil` or `Potion\: Healing`, is shown without the import's escapes (`Rope_coil`, `Potion: Healing`). A name typed otherwise, such as `\o/ banner`, keeps its backslashes.

A `$$` line needs no earlier line about the item. `$$ Potion of healing :used` on its own says the party had a potion and used it, whether or not anyone wrote it down when it was found. An item is held from the first line that names it until a `:sold`, `:used` or `:lost` line, and gone items fold away in the funds screen.

Opening an item's note, a note in the campaign's `Items` folder named after the item, shows the Party funds page with that item open: a panel above the purse with the item's name, who holds it (or, for a gone item, who last held it), whether it is held, sold, used up or lost, and the story written in its note below its properties, with its links. Its row is marked in the lists, and the gone items unfold when it is gone. *Change holder or status* opens the item's dialog, below. *Edit its note* shows the note on its [note page](#note-page), and *All items* closes the panel. When no session line names the item yet, the panel says so, shows its note all the same, and suggests a `$$` line that gives it to the party. The panel follows changes to the sessions and to its note.

**An item's note keeps its holder.** Its properties hold `holder`: who holds the item, as the panel shows it. It is a link, `holder: "[[Mira]]"`, when the session lines write the holder as a link; plain text, `holder: Old Tom`, when they write it plainly; and `holder: The party` when the party holds it. A gone item's note keeps who last held it. The session lines stay the record: the plugin writes `holder` from the session notes as they are saved, never from a line still being typed, when you open a campaign and each time a session note in the campaign you are in is saved, as when a `$` or `$$` line you typed is saved or the item's dialog writes one. A hand edit to `holder` is written over at the next save of a session note in the campaign, not when the item note is edited. It writes only the item notes whose `holder` differs, so saving a session with no holder changed writes nothing. When a note can't be written, a message says so once, and that note isn't tried again until the session lines give it another holder or other lines. A note in `Items` that no session line names is left as it is, and so is one Obsidian hasn't read yet. The write goes through Obsidian's own property editing, as the campaign settings do: it writes the whole properties block again, so comments in it can be lost, quoting can change, and a note without properties gets a properties block at its top. The text below the properties is left as it is, and the plugin reads the note again after each write and puts it back as it was if that text changed.

**An item's note holds its lines.** An item named on three or more lines in the campaign gets a note, `Items/<name>.md`, made when a session note is saved on this device, or, for sessions written before this version, once when the campaign is opened (see [Kind notes](#kind-notes)). Its properties hold `holder`, as above, and `lines`: every session line that names the item, in session order, written as in the session without its list bullet:

```markdown
---
holder: "[[Mira]]"
lines:
  - "$ [[Mira]] Silvered lantern"
  - "$$ Silvered lantern :changed to [[Baka]]"
  - "$$ Silvered lantern :sold 30gp"
---
Your own words about the lantern, never touched.
```

An item named on fewer than three lines gets no note of its own, but a note of it that is already in `Items`, in a folder inside it too, gets its `lines` and keeps its holder, its other properties and your words. `lines` is written only when a session is saved on this device, never when a change merely arrives by sync, and a note that loses all its lines stays with `lines` empty: the plugin never trashes an item's note. A name Obsidian forbids in a file name is made safe for the note's name only: each of `\ / : * ? " < > | # ^ [ ]` becomes a dash, so `Ring: +1` is noted in `Items/Ring- +1.md`, which keeps `aliases: ["Ring: +1"]` so `[[Ring: +1]]` still finds it (an alias you already have stays), while `Ring+1` is a note named `Ring+1.md`, as written. A name that can't be a note's name even so (one that starts or ends with a dot or a space, holds an invisible character, is a name Windows reserves or is too long) gets no note, and a message says why, once. Two item names that come to the same note name, whatever their capitals, don't share a note: the item named first keeps it, and the second gets none, with a message saying why, once. A note you made by hand, or before this version, is matched to its item by the same note name, whatever its capitals, its invisible characters or its kind of space.

Tapping an item on the Party funds page opens it: who holds it, and whether it is held, sold, used up or lost, with a price for a sale. A new holder or status is written as one of the `$$` lines above, naming the item as it was written, link and all, into the session you're in, passing over an open session earlier than the item's last line. A holder is written the way it was last written: one written in plain text, as in `:changed to Old Tom`, stays plain text, so no link to a missing note appears, and a linked one stays a link. A holder with a note in the campaign's `Characters` folder is offered as a link to it. Setting a gone item held again removes the line that took it, with its sale; an item named only by that line gets a `:changed to` line instead, so it stays. Changing how an item went replaces that line. *Sold for* shows a sold item's price as its line writes it, or nothing when the dialog couldn't write that line, such as `:sold -5 gp`. Correcting the price rewrites the `:sold` line where it stands, keeping its bullet and the words before ` :sold`; leaving the price as it was, or writing the same amount another way, writes nothing. Each is done only when that line says no more than the dialog writes, like `$$ Lantern :sold 30 gp`, and still reads as it did, on the line it was read from; for one with more words, change it in its note, which the dialog then offers to open. The dialog works from the notes as they were when it opened. Before it writes, it reads the session notes again: if they changed while the dialog was open in a way that changes how the item reads, even by one of its lines moving, it writes nothing and says so. Saving with nothing changed still writes nothing. A gone item can't be given to someone else while it stays gone, since the new holder's line would bring it back. Before writing, the plugin reads the notes as they would be after the change, and writes nothing unless every item comes out as asked and the purse moves by exactly the sale, or by the difference a corrected price makes. A new line is also refused when it would land in a code block, `%% %%` comment, `<!-- -->` comment or math block that never closes, where it would be hidden, and nothing is written. The same check runs again on the note's text as it is when the line is written, so a note changed meanwhile (a sync, a second window) is caught too.

How much an item matters is shown by how you write it:

| How it's written | What it is | On the funds screen |
|---|---|---|
| `found some rope` (no marker) | Doesn't matter | Not listed. It's just notes |
| `$ Potion of healing` | Matters for now | Listed, and folds away by itself after 3 sessions in which no line names it. Any later line about it brings it back |
| `$ [[Silvered lantern]]` | Matters to the campaign | Pinned at the top until a `:sold`, `:used` or `:lost` line. It has its own note in the campaign's `Items` folder, for its story. Pressing the link in the campaign tab before that note exists makes nothing and says the note doesn't exist inside the campaign yet; make it in `Items` from Obsidian's file list. It shows in Obsidian's graph |

An item can move up at any time: writing it once as `[[Potion of healing]]` makes it a key item from then on. `$$` lines take a linked name too: `$$ [[Silvered lantern]] :sold 30gp`. A linked and a plain name for the same item match, so `$$ Silvered lantern :sold 30gp` sells the key item as well.

A `$` line can hold two links, as in `$ [[Mira]] [[Flame Tongue]]`. A link to a note in the campaign's `Characters` folder is the holder, and any other link is the item. A link to a note that doesn't exist yet is the item, since anyone holding things has a sheet.

Telling the holder from the item isn't read yet, and neither is how much an item matters. Today the first link on a `$` line is always the holder, so `$ [[Silvered lantern]]` alone reads as nothing. Which tab of the funds page a line is on does not depend on that: any link on the line to your character puts it on your list (see [Mine and Party](#money)).

A block id at the end of an item line, as in `$ Rope ^r1` or `$$ Rope :changed to Old Tom ^r2`, is Obsidian's, not part of the item's name or its holder, so the dialog writes `$$ Rope …`. One left before the change word, as in `$$ Rope ^r1 :changed to [[Mira]]`, which earlier versions of the dialog wrote, isn't part of the name either. A `^` needs a space before it to start a block id. A line that took an item and ends in a block id says more than the dialog writes, so it is changed in its note, where the block id can be kept.

Typing `$$ lan` suggests the items held now that match, with who holds them, the same way, and picking one opens the item's dialog; once a ` :` and a change word follow, the line is an item line and no longer a lookup. Names match whatever their capitals and spacing. A name that is one link matches by the note it points to, whatever the link's alias or folder, while a longer name that holds a link (`+1 [[Longsword]]`) is a different item. A `$$` line with no `:` yet is still being typed and is read as nothing.

### Kind notes

Each session's `?`, `!` and `$` lines also appear in notes of their own, one per kind per session, linked back to the session:

```
D&D/Curse of the Pale Moon/
  Questions/Session 2.md
  Quests/Session 2.md
  Funds/Session 2.md
```

```markdown
---
session: "[[Session 2]]"
lines:
  - "? Who sent [[Lady Vess]] to the Old Mill"
  - "?= Who is the pale woman: [[Mira]]'s sister"
---
Your own words, never touched.
```

*Questions* holds a session's `?` lines and their `?+` and `?=` follow-ups, *Quests* its `!` lines and their `!+`, `!=` and `!x` follow-ups, and *Funds* its `$` lines, coin and item alike, and its `$$` lines that change an item. A follow-up is a line of the session it is written in, so an answer written in Session 3 to a question of Session 2 goes in `Questions/Session 3.md`. Lookups (`??`, `!!` and `$$` with no change) never reach a note. Lines are written as in the session, without a list bullet, in the order of the note. `session` is a link made with Obsidian's own link text, so two campaigns that both have a *Session 2* never link across.

- **The session is the truth.** `lines` is the plugin's, and the text below the properties is yours: the plugin never changes it, and it reads the note again after each write; if the text below the properties differs from before the write it never writes it again, so what you typed stays, and a message tells you to look at the note. Your own properties stay in place too, though the write goes through Obsidian's own property editing, which writes the whole properties block again (comments in it can be lost, quoting can change).
- **When.** A kind note is made or updated when a session note is saved on this device, from the Session notes page, *Edit all*, the note page, a dialog or *Clear notes*, once the plugin has read what was saved: never while you type, never from a kept draft, and never for a change that merely arrives by sync. A session saved in Obsidian's own editor isn't a save on this device in this sense: its notes appear at its next save made with the plugin, and *Fix*, below, only repairs a note that exists and differs. Deleting a session removes its lines from its notes.
- **When a note differs.** When a session changes by sync, or when the campaign is opened, and a kind note's `lines` differ from its session, one line is shown, such as *Questions for Session 2 differ from the session.*, with *Fix* and *Keep*; when the campaign is opened and several notes differ, one line counts them (*3 notes differ from their sessions.*) and *Fix* and *Keep* apply to all of them. *Fix* rewrites only `lines`, from what the session holds when it is pressed, and writes nothing for a session that has gone since. *Keep* leaves the note as it is until the next save of that session. Sync conflict files are never touched.
- **When a line is deleted.** It leaves its note. A note whose last line goes is moved to the trash if nothing of yours is in it, meaning no text below its properties, apart from blank lines, spaces and tabs, which count as nothing of yours, and no property but `session` and `lines`, read from the note itself just before; otherwise it stays with `lines` empty.
- **Notes that aren't the plugin's.** A note that is already at the path of a kind note is written only if its `session` property links that session: one of your own at `Questions/Session 2.md` with no such link is left alone, and a message says so once, as it does for a note that links another session. The plugin trashes a note only in a kind folder, only when that link matches, and only after reading it again. A completely empty file at a kind note's path (nothing in it at all, not even a space) that is more than a minute old is taken for a note the plugin began and couldn't finish, and is finished; a younger one, or a file with anything in it, is never taken for one.
- **Sessions written before.** The first time a campaign is opened after updating, the plugin makes the notes of every session that has lines and no note of that kind yet, and the item notes of items named on three lines, one at a time, and says so once: *Made notes for 4 sessions and 2 items.* It does this once per campaign, and keeps which campaigns it has done in its `data.json` (`notesMadeFor`). A note that is already there is never touched by it. It makes nothing while the campaign is still being read, and a session saved before that is read isn't acted on: its notes appear at its next save, or *Fix* repairs one that exists. It also does nothing for a campaign in which it saw no session. If a note couldn't be written, or another campaign was opened before it finished, the campaign isn't marked as done and the plugin tries again, for the notes still missing, the next time it is opened.
- **When a session is deleted and the later ones are renumbered.** *Delete session* moves the deleted session's notes to the trash by the same rule as a deleted last line; one that holds your words stays, and a message says that the session that takes the number will adopt it, *Fix* rewriting only its lines. Each later session's kind notes then move with it, lowest number first, from `Questions/Session 4.md` to `Questions/Session 3.md` and so on, and their `session` link is written again with the new name, only for notes whose `session` link names the session they followed and only when nothing is at the new path; your words move with the note. If the link can't be written after the note moved, the note is moved back when its old place is still free, and a message says so; when it can't be, the message says the note moved without its link and how to change it. A note that can't move (the one at its new path has your words, or it isn't linked to the session, or Obsidian hasn't read it) stays where it is and a message says so once; its link then points to the session that took the number, so use *Fix* on the sessions that moved.
- **If a write fails.** A message says so once, and that note isn't tried again until its lines change. A note whose properties couldn't be written is moved to the trash again if the plugin had just made it. Obsidian may not have read a note it just made yet: the plugin waits for it. The plugin writes `lines` and `session` (and, for an item's note, `holder`, `lines` and `aliases`) over properties of yours that have those names; that is by design, they are the plugin's. A value in `aliases` that isn't a text is kept.

A kind note's page is headed *Questions - Session 2*: its folder, a dash, and the session's name. This is only how the heading reads. The file stays `Questions/Session 2.md`, because the plugin finds, makes and renumbers a kind note by that name, and the `[[Session 2]]` links in your notes name the session.

Everything stays inside the Campaigns folder, through the gatekeeper. A kind note's path is `<campaign folder>/<kind folder>/<session name>.md`, which is inside the campaign, and the gatekeeper checks it again.

### People and places

A person or a place named on three or more `?`, `!` and `$` lines in the campaign gets a note of its own, in `Characters` or `Places`, when a session is saved on this device: never while you type, never from a kept draft, and never for a change that merely arrives by sync. The follow-up lines of a question or quest count, and so does a follow-up that matches no earlier line; lookups and plain text lines do not.

What a line says a name is:

| Line | The name is |
|---|---|
| A link after `from:` on a `!` line | A person |
| The holder link of a `$ [[Mira]] Rope` line | A person |
| `@[[Old Mill]]` | A place |
| Any other link | Not known |

A name that is a person on one line and a place on another is a place, and its note goes in `Places`, so `from: [[Old Mill]]` links to that place too. A name no line says anything about is asked about, in the list below, and until you answer it stays a plain link.

The new note holds one property, the session where the name was first named (the lowest session number), made with Obsidian's own link text:

```markdown
---
first named: "[[Session 2]]"
---
```

- **Only a name with no note.** A note is made only when Obsidian can find no note for the name anywhere in the vault, in every session that names it, and no note in the campaign has that name in any folder, whatever its capitals or the way its letters are written. So `[[Lady Vess]]` is linked to a note that is already there, such as one in `Characters`, `Fallen` or a folder of your own, and never made again.
- **New names.** After a save, a name on three or more lines that no line says is a person or a place is asked about once, in one small list: *New names in Session 2*, each name with a *Character* and a *Place* button. Pressing one makes the note at once, in `Characters` or `Places`, holding the same one property as above. Only names the saved session names are listed, and they are made the same way as any other: no name that already has a note, and none a file can't have. Closing the list, or pressing Escape, answers nothing and makes nothing, and the names are asked about again after the next save that names them. The plugin keeps no answer of "never ask": a name you leave stays a plain link. A list already on screen is not opened again over itself.
- **Never overwritten, moved or deleted.** The plugin makes a note only where there is none, and never changes, moves or trashes a note of a person or a place afterwards. If a note can't be completed, the empty file it had just made is removed, and nothing else.
- **Names a file can't have.** A name with a character a file name can't hold (`Lady: Vess`) or that would share a file name with another new name gets no note, and a message says so once.
- **Names are matched as written.** `[[Old Mill]]` and `[[old mill]]` are two names, but they would share a file name, so only the first gets a note and the second gets the message. A link with a folder in it, such as `[[Places/Old Mill]]`, can't be a note name and gets the message. A name that ends in `.md` gets the message too.
- **When it happens.** Once Obsidian has resolved the links of the saved session. A session saved in Obsidian's own editor, or one that arrives by sync, makes no note until the next save made with the plugin, and the earlier sessions of a campaign are not looked at when it is opened.
- **If a write fails.** A message says so once.

### A DM's campaign

Everything above is for a campaign whose main note does not say `role: dm`. In a campaign whose main note says exactly `role: dm`, the plugin does not guess what a name is from its line, and does not make a person's or place's note by itself. It asks you.

- **When it asks.** A `[[link]]` on three or more lines of the campaign, whatever kind of line each is (a `$` line, a `?` line, plain text), is asked about once, in the same small list as above: *New names in Session 2*, each name with a *Character* and a *Place* button, the buttons coming from the plugin's kinds. Pressing one makes that note at once, in `Characters` or `Places`, holding the same `first named` property as above. Closing the list or pressing Escape answers nothing, and the name is asked about again after the next save that names it. A list already on screen is not opened again over itself.
- **Only the DM.** The campaign's main note decides, for the campaign the session was saved in. A campaign with any other `role`, or none, is never asked, and keeps the behaviour described above, line guessing included.
- **A name you answered is not asked again.** Once a name has a note, in any folder of the campaign, it is not asked about, and neither is a name Obsidian already resolves to a note anywhere in the vault, since answering would make a second note of that name. A name already in the `aliases` property of any note of the campaign counts as that note, so `[[The Mill]]` is not asked about when `Old Mill` lists `The Mill` as an alias.
- **Characters and everything else.** A person you made a character is known in every campaign: a name with a note in the `Characters` or `Fallen` folder of any campaign of the vault, or listed in the `aliases` of such a note, is not asked about in another campaign. A place, or any other kind, is known only in the campaign it was made in, and the same name in another campaign is asked about there.
- **The same name.** `[[Places/Old Mill]]`, `[[Old Mill]]` and `[[old mill]]` are one name, as are `[[Old Mill#Cellar]]` and `[[Old Mill|the mill]]`. The folder is left off, and the name is written as the first line that names it wrote it. Each line counts once however often it links the name, and the lines of every session of the campaign are added together.
- **Code and comments.** A link in a code block (fenced with three backticks or three tildes), in code written in a line between single backticks, or in a `%% comment %%` is not counted.
- **Names a file can't have.** A name with a character a file name can't hold gets no question, and a message says so once.
- **When it happens.** Once Obsidian has resolved the links of the saved session, and only for names the saved session names. A session saved in Obsidian's own editor, one that arrives by sync, and the earlier sessions of a campaign opened for the first time do not start a question until the next save made with the plugin. A name made in this run stays answered until Obsidian restarts, even if you delete its note by hand.

## Character

A character is one note in the campaign's `Characters` folder, named after them. Their sheet is a view built from lines that state facts about them. It is never stored on its own.

A fact line starts with a link to the character, followed by `name: value` pairs. It has no marker: the `from:` and `reward:` on a quest line are quest facts, never character facts. Fact lines count in session notes and on the character's own note, where the link is left out (`AC: 16`). Anywhere else they are ordinary notes.

```markdown
[[Mira]] AC: 15, class: rogue
[[Brother Aldric]] type: Medium humanoid (human), lawful good
```

The sheet reads these names: `type`, `subtitle`, `speed`, `STR`, `DEX`, `CON`, `INT`, `WIS`, `CHA`, `class`, `AC`, `HP` and `alignment`. Any other name shows under the sheet's other values. Modifiers are worked out from the scores, never written.

Each value has a state, which comes from where its line is:

| State | Where the line is | On the sheet |
|---|---|---|
| Learned | In a session note | The value, linked to that session |
| Not known yet | No line states it, or the newest line in the sessions says `?` (`[[Mira]] HP: ?`) | Greyed out, with `?` |
| Override | On the character's own note, at the start of a line (`AC: 16`) | Marked so it never passes for something you saw |
| Carried over | On a character note in another campaign, named by the character's `carried from` property (see [Calling a character over](#calling-a-character-over)) | Marked with that campaign's name. Anything learned in this campaign wins over it |
| Changed over time | More than one line states it | The newest value, with the earlier ones and their sessions on tap. A list value (languages, say) adds them up instead |

"Newest" means the highest session number, and then the lowest line in that note. So a value marked not known shows again as soon as a later line states it. A `?` on the character's own note is read like any other override.

A name is letters and spaces, read whatever its capitals (`ac:` is `AC`). A value runs to the next comma that a name and a colon follow, so the comma in `type: Medium humanoid (human), lawful good` stays in the type, and a name with nothing after its colon states nothing. Learned values and overrides are read today, each with the note and line it came from, with an override winning over anything learned and the newest line winning among the rest. A session's properties are never read as facts, and a link counts for the note Obsidian resolves it to, so `[[Mira]]` and `[[Characters/Mira|her]]` state facts about the same character. Carried-over values and earlier values are read too. Other names are read whatever their capitals, so `Languages:` and `languages:` are one value, shown as first written. List values that add up aren't read yet: a list shows its newest line, with the others as earlier values.

On the character's own note, every line that starts with a name and a colon is a value, prose included, so `Personality: grumpy, but kind` shows on the sheet as *Personality*, marked as an override. That keeps the note to one format, and the sheet shows every such line, so none is taken for something seen at the table. To keep a line of prose off the sheet, start it some other way, such as in a quote (`> Personality: grumpy`), or without the colon (`Personality — grumpy`). Since such a line may be prose, the sheet asks for a second press before any change that would remove it (see [Character sheet](#character-sheet)).

### Making, renaming and deleting a character

*New character*, at the top of the Characters page, opens a dialog with the character's name, type line, subtitle and speed. It makes a note named after them in the open campaign's `Characters` folder, making the folder if it isn't there, and opens it. Each value given is written on the note as an override, one per line, and every other value starts as not known:

```markdown
type: Medium humanoid (human), lawful good
subtitle: Human Cleric 5
speed: 30 ft.
```

*Edit character* opens the same dialog filled in from the note's own lines, with a *Delete character* button. It is the *Edit character* button at the top of the character's [sheet](#character-sheet), the *Edit character* command in the command palette while their sheet is shown, and *Edit character* in the note's menu when you right-click it in the file list, or long-press it on a phone. Under each value the sessions have taught, the dialog shows it (*Learned in the sessions: 30 ft.*), so you can see what a value of your own would cover up.

- **Renaming** goes through Obsidian's file manager. With Obsidian's *Automatically update internal links* setting on (Settings → Files and links), it rewrites every `[[link]]` to the note, in session notes and everywhere else; with it off, links keep the old name. The note stays in its folder, and its path is written the way Obsidian keeps paths (`normalizePath`).
- **A changed value** rewrites the last line that states it, when that line states nothing else, keeping its bullet. When the last line that states it has other values on it, as in `AC: 15, speed: 30 ft.`, the new value is added as a line at the end of the note, which wins.
- **A cleared value** removes every line that states it on its own, so an older line can't bring it back. If a line with other values still states it, nothing is written and the dialog says so.
- **Lines it never writes to:** hidden lines are skipped, and a new line is added at the end instead. A line is hidden inside a fenced code block (a fence closes only at a bare fence of the same kind, at least as long), an indented code block (four spaces or a tab, at the start of the note's text or after a blank line or a code block), a `%% %%` or `<!-- -->` comment, or a `$$` math block, counted from below the note's properties. A math block opens at a `$$` with nothing after it on its line and ends at the next `$$`; a `$$` with words after it and no second `$$` on its line, as in an item line such as `$$ Rope :lost`, opens nothing; a line holding both marks is a one-line block. A math block opened with words on its first line (`$$ \begin{aligned}`) isn't recognised, so its closing `$$` is read as opening a block that never closes, and a note holding one refuses new lines, which is the safe direction. Marks inside `inline code` don't count. A line that ends in a block id (`speed: 30 ft. ^stats`) is left, since links may point to it: changing or clearing a value on such a line is refused.
- **A last check:** the changed note is read again before it is written. If it wouldn't give back exactly the values asked for, or if any line it wrote would be hidden, or any line it kept would become hidden or stop being hidden (as when a new line lands in a comment or code block that never closes), nothing is written. A value nobody changed is never written.
- **Deleting** needs a second press within four seconds. The note goes where Obsidian's *Deleted files* setting sends it (Settings → Files and links): the system trash, the vault's `.trash` folder, or nowhere, if it is set to *Permanently delete*. Every other note is left alone, so the session lines about the character stay, linking to a note that's gone.

The name and values are trimmed, then the dialog refuses, and writes nothing, when it's given:

| Refused | Why |
|---|---|
| A name another note in the folder has, whatever its capitals, compared after `normalizePath`, with invisible characters left out, every kind of space read as a plain space and letters composed the same way, so names that differ only by invisible characters or the kind of space count as the same name | Two notes can't share a name, and links would point at either |
| A name with any of `\ / : * ? " < > \| # ^ [ ]` or a control character (including the C1 controls) or a line or paragraph separator, or starting or ending with a dot or a space | A note can't be named that everywhere, or a link to it wouldn't work |
| Any invisible character, such as a zero-width space, a byte order mark, a text direction override or a Hangul filler, except: joiners only inside emoji (between two emoji, after a skin tone or presentation selector that follows one), the presentation selector only right after an emoji, and tag characters only in the flags of England, Scotland and Wales. Also half of a character, as text pasted in broken can hold | Nothing would show where it is, so two names would look the same. Any other run of tag characters draws as the same black flag |
| `CON`, `PRN`, `AUX`, `NUL`, `CONIN$`, `CONOUT$`, `COM0` to `COM9`, `COM¹` to `COM³`, `LPT0` to `LPT9` or `LPT¹` to `LPT³`, whatever the capitals, also with more after a dot | Windows keeps these names, so a vault synced there couldn't hold the note |
| A name whose file name would be over 255 bytes | Most file systems can't hold it |
| A value with a comma, a word and a colon in it, as in `Rogue 3, AC: 15` | It would read back as two values |
| A value with `%%` in it, or ending in a block id, as in `40 ft. ^stats` | The `%%` would start a comment hiding the rest of the note, and the block id would become the line's |
| A new name for a note that was moved or renamed since the dialog opened | The dialog would rename it from a place it no longer is. The dialog closes, since what it shows is out of date |
| A value changed in the note since the dialog opened | So nothing written meanwhile is lost. The dialog closes, since what it shows is out of date |
| A change that would turn the note's first lines into properties | So nothing is hidden |

A dialog with no name does nothing.

Fact lines are still read inside hidden lines today, so a value there shows on the card and the sheet, and neither the dialog nor the sheet can change it.

### Character sheet

A character's sheet is a page of the campaign tab, on the Characters page, with *← All characters* above it to go back to the gallery. Tapping a character's card on the Characters page, or a character on the dashboard, shows their sheet in the same tab, and opening the character's note in any other way shows it too (see [The campaign tab](#campaign)). Tapping a card in a gallery of another `.base` file opens the character's note, which shows the sheet. Obsidian's back button goes back to where it was opened from. The sheet follows the note when it is renamed, and Obsidian opens it again next time with the rest of the workspace. It writes nothing until you change a value. It redraws when the character's note, a note in their campaign, or the note they were carried from or a note in its campaign changes, is deleted or is renamed. If the notes can't be read, it says so in place of the values.

It shows the character's name, their subtitle when known, the six ability scores with their modifiers, then the type line, subtitle, class, Armor Class, Hit Points, speed and alignment, and every other value after them. Each value is drawn in its state's colour and says where it came from:

| State | Under the value |
|---|---|
| Learned | The session it was learned in, which opens the line |
| Override | *Override*, which opens the line on the character's note |
| Imported | *From D&D Beyond*, which opens the property on the character's note, then the working when the import gave one, then the route: *Printed on D&D Beyond's PDF*, or *Worked out here, from D&D Beyond (online)* |
| Carried over | *Carried from* and the campaign, which opens the line on the note it was carried from |
| Not known yet | *Not known yet*, which opens the `?` line when there is one |

Which value shows: his own override on the character's note first, then the imported value, then the newest value learned at the table, then a value carried over from another campaign. A value counts as imported only on a note with an `imported-from` property, and only from the import's own properties (see [Imported characters](#imported-characters)); an imported `species` gets a row of its own. Carried-over values include the other campaign's imported ones, under his overrides there.

A value with earlier lines shows how many (↺ 2). *Edit character*, at the top, opens the character dialog. *Update from D&D Beyond* beside it is on the sheet of every character in the campaign's `Characters` folder, whether or not anything was imported into the note before, and opens the [import dialog](#importing-from-a-pdf) for this note, with the online way and the PDF. The note doesn't hold a D&D Beyond number or link: the dialog asks for the link or the PDF each time, and the first update of a note you wrote by hand writes the import's properties and sections into it, listed for you to check first. *Import from D&D Beyond* on the Characters page is for a character with no note yet.

The override reader skips the import's five sections, from each `## … (from D&D Beyond)` heading to the next heading of level one or two, so a line typed there such as `Range: 60 feet` is never read as an override. It finds the sections with the note writer's own reader, so a heading inside a code block or comment is no heading to either: it neither ends a section nor starts one.

Under the values is the character's stat block, built from the values the sheet shows: their name, the type line and subtitle when known, then class, Armor Class, Hit Points and speed, and the six ability scores with their modifiers. It is the stat block the Characters page's cards show, in the same colours, and it shows carried-over values too. A value not known shows as a greyed `?`, never blank, whether no line states it or the newest line says `?`. The stat block only shows the values; they are changed by tapping them above it.

Tapping a value opens a dialog with the value, its earlier values newest first, each with its session (tapping one opens its line), and a button for each state. The button you tap saves the value typed in that state:

- **Learned at the table** adds `[[Mira]] AC: 16` at the end of the campaign's latest session, and clears the character's override, which would otherwise cover it. If the newest learned value is already the one typed, only the override is cleared.
- **Override** writes `AC: 16` on the character's own note, as the character dialog does: it rewrites the last line that states it on its own, or adds a line at the end. On a note the import wrote, a new line goes after your own text and before the import's first section, where the sheet reads it; the character dialog does the same.
- **Carried over** clears the override, so the value carried from another campaign shows again.
- **Not known yet** adds `[[Mira]] AC: ?` at the end of the campaign's latest session when a learned or carried value would otherwise show, and clears the override, as *Learned at the table* does. Like any learned line, it is newest only until a later session states the value again.

Enter saves the value in its own state, as learned when it wasn't known, and as an override when it was imported. On a value that shows from D&D Beyond, the dialog shows *From D&D Beyond* as the current state, which can't be pressed, and offers only *Override*, saying that an override is the only thing that shows over an imported value. Any dialog on a value with an import says *Change this on D&D Beyond too, or the next update will replace it.* Lines on the character's note are written and removed by the rules in [Making, renaming and deleting a character](#making-renaming-and-deleting-a-character), with the same last check.

Clearing an override removes every line on the character's note that states the value on its own. For the sheet's own names (`type`, `subtitle`, `speed`, the six scores, `class`, `AC`, `HP` and `alignment`) that happens on the first press. For any other name the line may be prose, so *Learned at the table*, *Carried over* and *Not known yet* need a second press within four seconds, as deleting does, and the dialog says why. *Override* rewrites the line with the value typed and needs only one press.

The sheet refuses, and writes nothing, when:

| Refused | Why |
|---|---|
| The value changed in the notes since its dialog opened | So nothing written meanwhile is lost. The dialog closes, since what it shows is out of date |
| Learned or Override with no value typed, or with `?` | `?` means not known; there's a button for that |
| A value with a comma, a word and a colon in it, with `%%`, or ending in a block id | As in the character dialog |
| Carried over when no carried note gives the value | There's nothing to carry |
| Carried over when the value was learned in this campaign | What was learned here wins over a carried value |
| Carried over when a `?` line in this campaign marks the value not known | That line wins over the carried value until a later line states it. The dialog says so before Not known yet is chosen over a carried value |
| Carried over with a value other than the carried one | That value belongs to the other campaign's note. Change it there, or choose Override |
| Learned at the table or Not known yet when the dialog opened with no session named | It never picks one at save time: the line would go somewhere the dialog didn't show. It says why: *There's no session to write in yet. Start one first.*, or that two session notes share the latest number and one must be renamed |
| Learned at the table or Not known yet when the session the dialog named has been moved, deleted or made again since, as when another session was renumbered into its name | The line would go into another session than the one shown. It says the session was moved or deleted |
| Learned at the table or Not known yet when the link wouldn't point to this character from the session | The line would be about someone else |
| Learned at the table or Not known yet when the new line would land in a code block, comment or math block that never closes | It would be hidden |
| A change on the character's note that the character dialog would refuse | As in the character dialog. Then the session line isn't written either |

The session line is written first and the character's note after it. If the note can't be changed by then, the sheet says the line was added but the note was left, so you can fix one of them by hand.

#### In the notes

After the stat block, *In the notes* lists every session line, in every campaign, with a link to the character, and says how many there are (*3 lines*). Lines in other notes, such as a place's note or another character's, aren't listed. It is built from Obsidian's own link index, so a link counts for the note Obsidian resolves it to, as for fact lines: `[[Mira]]`, `[[Characters/Mira|her]]`, `[[Mira#Stats]]` and an embed, `![[Mira]]`, all count. A line with two links to them shows once. Links in a session's properties aren't lines, so they don't show. Obsidian doesn't index links in code blocks or comments, so lines there don't show either.

Each line shows as written, without its bullet, with its session under it (*Session 12*), and the campaign too when it isn't the character's own (*Session 2 · Ashen Road*). Tapping it opens the session at that line; tapping a link in it opens the link. The character's own campaign comes first, then the other campaigns by name, each campaign's lines together. Within a campaign the newest session comes first, and in each session the last line first, since it was written last. With no line yet it says *No session mentions [[Mira]] yet.* If the sessions can't be read, it says so.

A renamed character keeps their lines when Obsidian's *Automatically update internal links* setting is on, since every link is rewritten to the new name. With it off, the old links point nowhere, and their lines leave the list until the links are fixed.

The lines are read when the sheet opens, and read again when Obsidian has resolved the links of a session that's on the list or now links to the character, and when a session on the list is deleted or renamed, once changes have settled for a moment. When the rest of the sheet redraws, the list is drawn again from the lines already read. A changed note is checked by its own links only, so writing elsewhere in a big vault costs a look at that note's links and no more.

### Imported characters

Built in steps. The note writer (`src/imports/note/`, with the names it shares in `src/imports/layout/`), the import dialog for a PDF (`src/imports/dialog/`), the sheet's inventory, purse, spells and features panels with tracking (`src/characters/imported/`, `src/funds/tracking/`) the [agreement](#the-dd-beyond-agreement) the online route asks for (`src/imports/agreement/`) and the [online route](#importing-online) itself (`src/online/`, the one place with network code) are in.

An import goes into the character's own note. Nothing else is touched.

- **Properties.** The import writes `imported: 2026-11-13` and `imported-from: pdf`, then each value it knows: `class`, `species`, `AC`, `HP`, `speed`, `STR`, `DEX`, `CON`, `INT`, `WIS`, `CHA`. A value the source does not give is left out, never guessed, and an older import's value for it is removed. Text values are written in quotes, with anything that could act as markup made inert (so a backslash may show before a character such as an underscore).
- **Names are matched exactly.** The import replaces a property only when its name is exactly one of the names above, with or without quotes around it (`"AC":` and `'AC':` count as `AC`). A property that only differs by capitals (`ac:`, `Speed:`, `Hp:`) is yours, so the import refuses and names it, rather than overwrite it or write a second one beside it.
- **Sections.** Five sections, each headed `## <Name> (from D&D Beyond)`: *Numbers*, *Inventory*, *Purse*, *Spells* and *Features*. Every line is a bullet (`- Rope × 2`, `- gp · 12`, `- AC · 18 · Printed on D&D Beyond's PDF`), and imported text in it is made inert, so it can't read as a link, a marker, a fact line or a heading. A section runs from its heading to the next heading of level one or two, without the blank lines at its end, which stay yours. A heading inside a code block or a comment (`<!-- -->` or `%% %%`) is not one, and neither is a heading underlined with `===` or `---` (a setext heading): it does not end a section, and its lines count as typed text in it. A section the import has nothing for is not written, and one it wrote earlier is removed. A section that is missing is added at the end of the note, before its last line break.
- **Left out.** A PDF can hold lines too long or not clean enough to bring in. Each section that lost lines ends with `- Left out: 2 too long, 1 not clean`, so the count stays with the note. The text of an item can't make this line, since a colon after a leading word is escaped.
- **Update** reads the note first and writes only when something would change. It rewrites only those properties and sections, in place. Everything else is kept line for line, in the note's own line breaks. Before writing, the new text is compared with the old one outside the import's properties and sections, and any difference refuses the write; the write itself refuses when the note changed since it was read. An update that changes no value writes nothing, not even the date.
- **Typed text** inside a section, meaning any line that is not one of the plugin's `- ` bullets, goes when the section is replaced. What an update would replace is listed value by value, with the typed text listed apart as a warning, and the update refuses unless it is given exactly that list back. A typed bullet is replaced and listed with the other lines, but is not in the warning.
- **Refused, with nothing written:** a note with the same plugin heading twice; a note that ends inside a code block or comment that is never closed (a section written there would be hidden); a note of more than 100,000 lines; a property line of more than 20,000 characters; any other line of more than 50,000 characters; a name that only differs by capitals from the import's.
- **Making the note.** A new character's note is named for them in the `Characters` folder, and refused when the name is not a safe file name or another note already has it, whatever its capitals. Writes go through the gatekeeper, only to a note directly inside the `Characters` folder.
- **Matching.** A note named for the first words of the character's name, or for more of it (`Thessaly` for `Thessaly Brightwater`), is offered, the closest first.

#### Importing from a PDF

*Import from D&D Beyond* on the Characters page, and *Update from D&D Beyond* on the sheet of a character in `Characters`, open one dialog. It offers the [online way](#importing-online) first, and below it the PDF that D&D Beyond's *Export to PDF* makes (open your character, choose *Manage* next to the name, then *Export to PDF* at the bottom of the menu), from anywhere on the device; the file is read in memory and never copied into the vault.

- A file over 10 MB is refused before it is read. The PDF reader's and the sheet's own refusals are shown in words, and the dialog asks for a file again. *Update* refuses a PDF for another character: *This PDF is for Primary Monk, not Secondary. Nothing was changed.*
- Anything that goes wrong other than a refusal is shown as a plain sentence (*Something went wrong while reading the note, so nothing was written.*, or *…while writing the note. Look at the note before you try again.*), never as the error's own words.
- The dialog then shows the character's name, species and class, how many items, spells and feature lines come in, how many lines were left out of each list (too long or not clean), and that the PDF doesn't give proficiency marks, attacks, alignment, spell slots, total level, hit dice or carrying capacity.
- *Import* matches the name to the notes directly in the campaign's `Characters` folder. When a note is named for the first words of the character's name, or more of it, it asks which note this is, closest first, with *Make a new note* last; with none, it goes straight on to a new note.
- For a note that exists, it lists every property and section line the update would replace, with text typed inside the import's sections listed first as a warning. *Update* writes exactly that; if the note changed since, it refuses in words, writes nothing, shows the refusal above the changes as they are now and offers *Update* again. When nothing would change it says so and offers only *Close*.
- For a new note, a name that isn't a safe file name or that another note has is refused before *Import* is offered.
- After a new note is written its sheet opens. *Choose another file* goes back to the start.

#### Importing online

The same dialog's first part is the online way. It says *Bring your character in from D&D Beyond. Only your character's number is sent, to one address, and this plugin adds no login, cookies or other headers of its own. Nothing is saved until you press Import.*, with a box for *Your character's link or number* and *Bring in from D&D Beyond*. Nothing is sent before that button is pressed.

- **What is sent.** One GET to `https://character-service.dndbeyond.com/character/v5/character/` followed by the digits of the number, 1 to 12 of them, taken from a bare number or a `dndbeyond.com/characters/<digits>` link (with or without `https://` and `www.`, and anything after the digits). Nothing else typed reaches the address: not the rest of a link, not a query. This plugin adds no login, cookies or other headers of its own, and no body; Obsidian sends the call and may add its own details, and follows redirects.
- **The first press** asks [the agreement](#the-dd-beyond-agreement) if this device hasn't given it. *Use a PDF instead* (or closing it) sends nothing and says so; the link stays typed.
- **One at a time.** While a call is waiting, including one that has timed out but not yet ended, another press sends nothing and says *Still waiting on D&D Beyond.* A press less than ten seconds after the last one that sent (counted from that press, not from its answer) sends nothing and says to wait. The first press ever is never held back.
- **Fifteen seconds.** After 15 seconds the plugin stops waiting and says so; an answer that comes later is dropped and never shown or written. There are no retries, no polling and no caching.
- **What is accepted.** Only status 200, a content type starting `application/json` (in any capitals), a body of at most 5,000,000 bytes, text that reads as the character's data by the same reader as everything else, and the number inside it being the one asked for. Otherwise one plain refusal: *D&D Beyond didn't send this character. Check it is set to Public.* (403), *No character has that link.* (404), *That reply wasn't a character's data.* (any other status or content type), *D&D Beyond sent a different character than the one asked for, so nothing was brought in.*, *Couldn't reach D&D Beyond. Check your internet connection, or use the PDF.*, or *D&D Beyond didn't answer within 15 seconds…*. A refusal shows in the same dialog with the link as typed, the button again and the PDF below it.
- **Redirects.** Obsidian's `requestUrl` follows them and cannot be told not to; the checks above are on whatever finally answers.
- **What comes in** is shown for review exactly as a PDF's is, with the route *Worked out here, from D&D Beyond (online)*, and nothing is written until *Import* or *Update* is pressed. The character's backstory and notes are never read. AC and maximum hit points are not stated by D&D Beyond's data, so they show as not known.

#### On the sheet

Under the values, a sheet with an import shows four panels, read from the import's sections and never written from: *Inventory*, *Purse*, *Spells* and *Features*. Each line shows as plain text, with the import's escapes taken off. A list with nothing in it says *Nothing came in for this list.* A list the PDF lost lines from says so in plain words, from its `- Left out:` line: *Left out of the PDF's list: 1 line too long to bring in and 2 lines that couldn't be read as plain text.* Below the panels, a PDF import says once that the PDF doesn't give proficiency marks, attacks, alignment, spell slots, total level, hit dice or carrying capacity.

- **Inventory.** Each item shows its count when the import knows it (`× 2`). When the sheet's character is in the campaign the tab shows, each item not held on the Party funds page has *Track on the funds page*, and the others say where they stand: *On the funds page* when the character or the party holds it, *Held by Secondary, on the funds page* when someone else does (*Held by another note named Primary Monk, on the funds page* when its holder link leads to another note of the character's name, such as `[[People/Primary Monk]]`), and *Sold, on the funds page* (or *Used up*, *Lost*) for an item gone from the page, which can be tracked again. Items are matched by name, ignoring capitals, runs of spaces and the import's escapes, so `Rope (50 ft) *silk*` typed at the table and the import's `Rope (50 ft) \*silk\*` are one item. *Track* is offered only for a line as the import writes it: a line typed into the section by hand, or a name longer than the 100 characters the import writes, gets no button. A name the import had to guard at the start of its line, such as `Potion\: Healing`, `\(Ammo) Arrows`, `\"Lucky" Charm`, `\+1 Dagger`, `1\. Arrows` or `\~Cloak`, is as the import writes it and can be tracked; the same name typed without the guard, `Potion: Healing`, can't. A character of another campaign gets no buttons, and the panel says to show that campaign first; a character in no campaign's `Characters` folder is told its items can't be tracked.
- **Track on the funds page** opens a small dialog: the item, *Held by* the character, the session it writes into (the campaign's latest), and the exact line it will write. *Save* adds that one line, `$ [[Primary Monk]] Rope`, with the item's name as the note holds it, so it stays inert. An item the funds page already has, such as one sold, is written as the funds page wrote it, so it stays one item there, but only when that text is itself inert: written as the import would write it (`Rope (50 ft) \*silk\*`), or one plain link (`[[Rope]]`, with no `!`, `|`, `#` or `^` and a name that needs no escape). Anything else the funds page wrote for it (`Rope (50 ft) *silk*`, `Rope #loot`, `Rope [weight:: 5]`, `![[map.png]]`, a Markdown link, inline code or a highlight) is refused, in words, and nothing is written: write that line in the session by hand. Before writing, the plugin reads the notes as they would be after the line: it writes nothing unless exactly one new item comes out, held by that character, with every other item unchanged. It checks again against the session note as it is at the moment of writing. So a name the ledger would read as coin (`Pouch 10 gp`) or an item already held on the page is refused, in words. A count isn't tracked: the funds page holds the item, not how many.
- **On the funds page, but not on this import.** Items the funds page has as held by the character that this import doesn't list are marked under the inventory, each with *Used up*, *Sold*, *Lost* and *Changed*. An item counts as the character's when its holder link leads to the character's note, so `[[People/Primary Monk]]` is another note's. Each opens the existing item dialog with that status chosen (*Changed* as it is, to give it to someone else); nothing is written until you save there. From a PDF this can't tell a renamed line from a gone item, so a marked item may only have been reworded on D&D Beyond. A note with no inventory section marks nothing, and when the import left lines out, the panel says some marked items may be among them.
- **Purse.** The coins the import gives, as on the Party funds page (`1,200 gp`, `? ep` for one not known, none at zero), and that it is not added to the party purse.

#### The D&D Beyond agreement

Before the online route sends anything, you agree to it once on each device. The words are the same everywhere they are asked:

> **Fetch your character from D&D Beyond?**
>
> To bring your character in, this plugin sends one message to one address, character-service.dndbeyond.com. The message holds your character's number and nothing else. This plugin adds no login, cookies or other headers of its own, and it never touches your D&D Beyond account. Obsidian sends the message and may add its own details and follow redirects.
>
> Your character has to be set to Public on D&D Beyond. A public character's backstory and notes can be read by anyone who has the link, not only by this plugin. The plugin throws them away before it reads anything and never saves them in your vault. You are responsible for keeping the link or number of your public character safe, because anyone who has it can read that character.
>
> You are asked this once on this device. After you continue, the button fetches only when you press it. If you would rather send nothing, bring your character in with its PDF instead.

- **Where it is asked.** On the [welcome page](#welcome-page), as the step *Bringing your character in*, with *Agree* and *Not yet*; and in a dialog at the first press of the online button, with *Continue* and *Use a PDF instead*. Closing the dialog without a choice is *Use a PDF instead*. Whichever comes first on a device decides it there, and the other never asks again on that device. Neither button is highlighted over the other.
- **Where it is kept.** *Agree* and *Continue* write `true` under `dungeons-and-dinthla-beyond-agreement` in Obsidian's own storage for this vault on this device, beside the text typed and not yet saved. It is never written to the vault or to the plugin's `data.json`, so a vault synced to another device can't carry it there, and the same key found in `data.json` counts for nothing. Only `true` counts: anything else held under the key is no agreement.
- ***Not yet* and *Use a PDF instead* keep nothing.** The welcome page moves on and shows the step again only when the page is shown again with *Show this again*; the online button asks at its next press.
- **The online button asks it.** The first press of *Bring in from D&D Beyond* shows the dialog unless this device has agreed, and sends nothing until it has. The answer can't be taken back yet: there is no setting for it.

#### Your character's purse on the Party funds page

The Party funds page shows the purse of the player's own character (named by the campaign note's `character` property) at the top of its *Mine* tab, titled *Primary Monk's purse*, when that character's note has an import. It is shown apart from the party purse, which is in the *Party* tab, and never added to it. It is not the *Your purse from the ledger* panel below it, which adds up the coin lines that link your character. It redraws when a note in the campaign's `Characters` folder or the campaign note changes, so naming a character in the campaign note shows its purse. If the note can't be read, it says *Couldn't read your character's note, so its purse isn't shown.* in its place.

### Leaving play

Your character can leave play as *Died*, *Retired* or *Backup*. The question comes when another character is to become yours: after *Import from D&D Beyond* writes a character who isn't yours yet, when you press *Make main* on a backup or on a fallen character, and after *Update from D&D Beyond* on a character whose note says they died or retired. The dialog, *Make Secondary your character*, asks *Primary Monk is your character now. What happened to them?*, with an optional box, *What were they last doing?*, and *Died*, *Retired*, *Backup* and *Not now*. When the campaign has no character yet, it says so and offers only *Make main* and *Not now*. Nothing is written until you press one, and *Not now* writes nothing. A note that is already your character is never asked about, unless a switch to it was left part done (see below).

The character's own note moves. *Died* and *Retired* move `Characters/<Name>.md` to `Fallen/<Name>.md` in the campaign, making the `Fallen` folder if it isn't there, through Obsidian's own rename, so links to them follow. There is no separate record: the note is the character. *Backup* leaves the note where it is.

Before the first write, the plugin works out every change and checks each one. Then it writes in this order:

1. The old character's note gets `standing: died`, `standing: retired` or `standing: backup` among its properties and, for *Died* and *Retired*, a snapshot added at the bottom (below).
2. For *Died* and *Retired*, the old note moves to `Fallen`.
3. A new character who is in `Fallen` moves back to `Characters`.
4. The campaign note's `character` property names the new character, `character: "[[Secondary]]"`, as Obsidian would link it from the campaign note once the note is where it will stay.
5. The new character's `standing` is taken off, so a backup or a fallen character who comes back is played again. Their snapshots stay in their note.

The snapshot is added to the end of the note, dated:

```markdown
## Left play on 2026-11-12
Died on 2026-11-12, after [[Session 7]].
Last doing: holding the bridge at the Old Mill.
### Open questions
- What is under the mill?
### Active quests
- Clear the cellar
### Latest coin
- 40 gp reward
### Items held
- Silver dagger
```

It holds the three newest open questions and active quests, the three latest coin entries and the items they held, newest first, from the campaign as it is when you press. A list with nothing in it is left out. The session is the campaign's latest, when one number is the highest. *Last doing* is there only when something was typed. Everything taken from the notes or typed is made inert first, as an import is, so it can't read as a link, a tag, a heading or a fact line. What they were last doing has to be one line of at most 300 characters, and *Backup* ignores it. When a character who came back leaves play again, another snapshot, dated that day, is added under the first.

If a step fails, the message names every write that was done and the one that wasn't, and says to press *Make main* again. Pressing *Make main* finishes what is left, without a second snapshot: the dialog then says the old character has already left play, or that the new one is already named in the campaign note, and offers only *Make main*.

- **Refused, with nothing written:** a note that already has the name in `Fallen` (or, coming back, in `Characters`), whatever its capitals (rename or move it first); a campaign note that changed, or a character's note that was moved or deleted, since the question was asked; a campaign note whose `character` isn't one whole link, like `[[Name]]`, to a note directly in the campaign's `Characters` or `Fallen` folder (a link to a note that was deleted counts as no main, so the chosen character replaces it); a note that has `standing` or `character` twice, or under other capitals; a property with a blank or comment line right next to it; and a change that would make the note's properties read differently than only that property, which Obsidian's own reading of them is compared for, before and after.
- **Only those properties change.** Each property is written through the gatekeeper, and before writing, the note's new text is compared with the old: everything but that one property must be the same, line for line, and the properties as Obsidian reads them must be the same too, or nothing is written. The write itself refuses when the note changed since it was read.
- **Other campaigns.** A character can be imported into another campaign, even one who died elsewhere. Each campaign keeps its own notes, its own `standing` and its own `Fallen` folder; leaving play in one changes nothing in another.
- **A fallen character is not updated.** *Update from D&D Beyond* refuses a note in `Fallen`, and the button is not offered there. Bring them back with *Make main* first.
- **No second note.** *Import from D&D Beyond*, *New character* and renaming a character in the sheet's edit dialog refuse a name that a note in this campaign's `Fallen` has, whatever its capitals: *Primary Monk is in this campaign's Fallen folder, so no second note was made for them. Make them main from the Fallen list to bring them back.*

### Calling a character over

Calling a character into another campaign is a choice, made in a dialog: everything, only the groups you pick (ability scores, other values, history), or only a link. The new campaign's note for them records it in two properties:

```markdown
---
carried from: "[[Ashen Road/Characters/Mira]]"
carried: [abilities, values]
---
```

Only the groups listed in `carried` show on the sheet as carried over: `abilities` for the six scores and `values` for everything else. The sheet reads the carried note's values as its own sheet would, from its campaign's sessions and its own overrides. Until the dialog is built, the two properties can be written by hand. `history` isn't read yet. The same dialog works as a library: it can call over anyone from any other campaign, or from the game system's own notes, which are there before the first campaign.

### Characters page

The campaign tab's *Characters* page shows a card for each Markdown note in the campaign's `Characters` folder, the player's own first and the rest by name, and redraws when one is added, changed, renamed or deleted, or when the campaign note changes. Opening the campaign's `Characters.base` shows this page too, and opening a character's note shows it on their sheet.

The same cards are also a view the plugin adds to Obsidian's Bases, named *Characters*, for a `.base` file that lists character notes, such as a `Characters.base` at the campaign's top. Bases does that file's filtering and sorting, and the plugin draws the cards, with the player's own character moved first and the rest in Bases' order. The plugin no longer writes `Characters.base`, and the one at a campaign's top now opens the Characters page instead of Bases; the view still works for any other `.base` file. Registering the view is why `minAppVersion` is 1.10.3.

Each card is a short stat block: the character's name, their `type` and `subtitle` when known, then `class`, `AC`, `HP` and `speed`, and the six ability scores with their modifiers. A value no line states, or marked not known with `?`, shows as a greyed `?`, and a type line or subtitle marked not known is left out. Carried-over values aren't on the cards yet; the sheet's stat block shows them. Each card reads the sessions of the campaign its note is in, even while another campaign is open, and a note outside any campaign shows only its own overrides. The player's own character, named by a link in the campaign note's `character` property, comes first and is marked *Your character*, and changing that property redraws the cards, on the dashboard too, so the new one moves to the top. Tapping a card opens the character's [sheet](#character-sheet). With no characters yet, the page says to add one with *New character*. *Import from D&D Beyond*, beside *New character*, opens the [import dialog](#importing-from-a-pdf).

A character who [left play](#leaving-play) is not among the others: their note is in the campaign's `Fallen` folder and they are listed under *Fallen*, below the backups, each marked *Died* or *Retired* with *Make main*. The dashboard doesn't show them. A note in `Characters` that says it died or retired, which only a switch that stopped part way leaves, stays with the others, marked, with *Make main* to finish it. Backups are listed under *Backups*, each with *Make main*. A backup is a note with `standing: backup`, or a note with an import (`imported-from`) that has no `standing` and isn't your character: an imported character you haven't made yours yet is kept ready the same way. Your own character is never listed as a backup, whatever their note says.
